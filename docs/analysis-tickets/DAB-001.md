# DAB-001: Hybrid-RAG fallback `try` spans response delivery, producing a duplicate reply and a duplicate bill

- Type: BUG
- Severity / Payoff: **S1** (recalibrated; owning lanes filed S3 "S2 latent" and S2 "SUSPECTED")
- Effort: XS (6-line diff)
- Priority score: 16.0 — impact Critical (4) x frequency Occasional (2) / effort XS (0.5)
- Confidence: **VERIFIED** — a failing test was written against unmodified production code
- Merged IDs: `B1-01`, `B8-06`, reproduced by `I6-03`
- Blocks / Blocked by: blocked by nothing. Should land before any mutation-testing harness, which
  uses a green baseline as its guard.

## Context

`DiscordBot._process_message_with_context` wraps hybrid RAG retrieval in a `try` so that a
retrieval failure can fall back to the legacy `ContextCollector` path. That `try` also encloses
`await self._generate_and_send_response(...)`, which is not a pure computation — it sends the
status message, calls Gemini, and delivers the reply.

Any `Exception` escaping delivery is therefore misread as "hybrid RAG failed". The handler logs one
WARNING, collects legacy context (an extra `select_relevant_context` LLM call), and calls
`_generate_and_send_response` a **second** time with the same message. Nothing records that the
first attempt already produced side effects.

Three lanes found this. Two hedged — B1 rated the symptom "partially REFUTED" because
`response_generation.py:486`'s `except Exception` is a total sink for anything raised *after* the
status message is sent, and B8 rated the double-send "SUSPECTED". The improvement lane built the
reproduction and the hedge collapsed: the sink does not cover errors raised by
`Typing.__aenter__`, which is reached before the coordinator's own try.

This is also the mechanism that makes a completely dead RAG stack invisible. As `AGENTS.md` puts it,
"a broken RAG change looks like nothing happened".

## Acceptance criteria

- [ ] `_generate_and_send_response` is called at most **once** per inbound message, on every path.
- [ ] A retrieval failure (an exception from `hybrid_context_retriever.retrieve`) still falls back
      to the legacy `ContextCollector` path and still logs one WARNING naming the cause.
- [ ] A **successful but empty** retrieval (`[]`) does **not** fall back. The gate is
      `rag_context is not None`, not truthiness — an empty retrieval is a successful retrieval.
- [ ] A delivery-time exception propagates to the outer handler and produces exactly one
      user-visible error, not a second full generation cycle.
- [ ] `python -m unittest discover -s tests -p "test_*.py"` passes from the repo root. The count
      rises from 125 by the number of tests added.

## Files to touch

- `src/bot/discord_bot.py` — the `911-940` block. The 6-line hoist:

```python
if self.config.rag_enabled and routed_intent != "image_generate":
    rag_context = None
    try:
        rag_context = await self.hybrid_context_retriever.retrieve(...)
    except Exception as exc:
        logger.warning("Hybrid RAG failed for message %s; using legacy "
                       "context fallback: %s", message.id, exc)

    # Only *retrieval* may fall back. A delivery failure below must reach the
    # outer handler, never re-enter the legacy path and answer a second time.
    if rag_context is not None:
        await self._generate_and_send_response(...)
        return
```

- `src/bot/response_generation.py:494-516` — **optional, second change.** Widen the outer handlers
  to `except Exception` (or wrap the `typing()` acquisition separately) so aiohttp-level errors are
  reported once instead of silently re-running. This is not required to make the new test pass.
- `tests/test_context_fallback.py` — new file.

One placement decision to make deliberately: I6 keeps `rag_context = None` **inside** the
`if self.config.rag_enabled ...` block; B1 hoists it **above** the `if`, which also covers the
`routed_intent == "image_generate"` branch. Pick one and comment why.

## Test to add

`tests/test_context_fallback.py`, `IsolatedAsyncioTestCase`, 9 tests split happy-path / fallback.
The load-bearing one is
`test_a_failure_after_delivery_is_not_retried_through_the_fallback`: stub retrieval to succeed,
stub `_generate_and_send_response` to raise on first call, assert it was awaited **exactly once**
and that `context_collector.get_channel_context` was never awaited.

If the defect returns, that assertion fails with `2 != 1`.

Assert the fallback is **audible**: use `assertLogs(..., WARNING)` with the cause embedded. That log
line is the only signal an operator gets that RAG is down.

## Risks and notes

- **Nothing existing breaks.** All 125 tests stay green before and after; the count only rises.
- Using `if rag_context:` instead of `if rag_context is not None:` silently reintroduces a second
  full generation cycle for every empty-but-successful retrieval. This is the single most likely
  way to get the fix wrong.
- The second change (widening `response_generation.py:494-516`) alters which exceptions reach the
  user-visible error path. Land it as a separate commit so it can be reverted independently.
- `asyncio.CancelledError` is a `BaseException` and is not caught by the fallback's
  `except Exception`, so shutdown and cancellation do not produce duplicates today and must not
  start to.
