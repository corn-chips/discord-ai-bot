# DAB-002: `on_ready` swallows `setup_commands` failure, permanently disabling live mode, personality and user preferences

**Status: LANDED** in `82b38a3` — the three personalization services are built eagerly in `DiscordBot.__init__`, so a registrar raising can no longer decide whether they exist. The S1 is closed; **three acceptance criteria below are not**, all of them observability: there is no durable degraded marker, `get_service_health_status` still hardcodes `✅ Available` for four core services (`discord_bot.py:758-761`), and the ready banner at `:711` still fires unconditionally. Criterion 6 (naming *registration* rather than *sync*) did land, in `a55c601`.

- Type: BUG
- Severity / Payoff: **S1** (recalibrated; B1 filed S2, C2 filed S1)
- Effort: S (~30 min for the eager-construction half; the visibility half is another S)
- Priority score: 8.0 — impact Critical (4) x frequency Occasional (2) / effort S (1)
- Confidence: **VERIFIED** by two independent lanes and one independent verification pass
- Merged IDs: `B1-02`, `C2-06`; fix prototyped as `I1-01`, visibility as `I1-21`, isolation as `I1-23`
- Blocks / Blocked by: blocks `DAB-009`. Blocked by nothing.

## Context

`register_personalization_commands` is the **last** call in `setup_commands`
(`src/bot/commands.py:91`), and it is the only place that attaches
`_channel_settings_service`, `_user_prefs_service` and `_message_visibility_service` to the bot.

Any earlier registrar that raises aborts `setup_commands`. `on_ready` catches the exception, writes
one `logger.error` — mislabelled **"Failed to sync slash commands"** when the failure was in
*registration* — and continues straight to `_start_automatic_rag_backlog` and
`"Bot is ready and listening for mentions!"`.

The result is a bot that reports full health while live mode, per-channel personality and per-user
preferences are silently dead, and most of the command tree never registered.

Note: `AGENTS.md` claims `_pin_service` is also attached during registration. That is **wrong**;
`discord_bot.py:364` constructs it in `__init__` and `personalization.py:138-142` only reuses it via
`getattr(bot, "_pin_service", None) or PinService(...)`. Pins therefore survive this failure; the
other three services do not.

## Evidence

- Swallow: `src/bot/discord_bot.py:530-542`, `except` at `:541`. (The full `on_ready` body is
  `:461-546`; that wider range belongs to `DAB-003`.)
- Attach sites, all inside the last registrar: `src/bot/command_modules/personalization.py:43`
  (`_channel_settings_service`), `:146` (`_message_visibility_service`), `:380`
  (`_user_prefs_service`). The improvement lane cites `:37` and `:376` for the same two;
  verify against the tree before writing the diff.
- Registration order: `src/bot/commands.py:73-91`.
- The existing correct idiom to copy: `personalization.py:138-142`,
  `getattr(bot, "_pin_service", None) or PinService(...)`.

Downstream consumers that read absence as "off":

- `discord_bot.py:705-713` `_is_live_mode_enabled` short-circuits to `False` for every channel.
- `discord_bot.py:157-159`, `:260-262` `_get_personality_prompt` returns `None`.
- `discord_bot.py:1089-1093` `_resolve_request_preferences` skips the user's model and language.

B1 probe (`/tmp/b1probes/probe_b1_02_setup_swallow.py`), injecting a failure into
`register_usage_commands`:

```
on_ready swallowed: RuntimeError: simulated failure inside register_usage_commands
  hasattr(bot, '_channel_settings_service') = False
  hasattr(bot, '_user_prefs_service') = False
  hasattr(bot, '_message_visibility_service') = False
  DiscordBot._is_live_mode_enabled(bot, 123) -> False
  commands registered before the failure: 8
```

Independent verification (V2, `/tmp/v2s1b2/p5_registrar.py`) reproduced it and found the blast
radius **understated** — 14 of 22 top-level commands also vanish:

```
--- break_registrar = register_usage_commands ---
  commands registered      : 8
  _channel_settings_service: False
  _user_prefs_service      : False
  _pin_service             : False
  _message_visibility_svc  : False
  live mode for channel 42 : False
  operator-visible logs    :
      ERROR src.bot.discord_bot: Failed to sync slash commands: simulated registrar bug
      INFO  src.bot.discord_bot: Bot is ready and listening for mentions!
```

V2's one correction: "permanently for the process lifetime" is imprecise. discord.py re-fires
`on_ready` on every re-IDENTIFY, so a *transient* cause (one of the `_ensure_table()` calls hitting
a locked SQLite file) self-heals on reconnect. A *deterministic* cause (a bad decorator, a typo, a
description over 100 chars) fails identically every time and is effectively permanent.

Realistic triggers named by B1: a jinja2 template-loading error in the report/usage registrars, a
duplicate command name after a refactor, a `sqlite3.OperationalError` from a service constructed
inside a registrar, `app_commands` validation rejecting a description longer than 100 chars.

## Reproduction

1. Patch any registrar in `src.bot.commands` other than the last to raise.
2. Await `DiscordBot.on_ready()` against a stubbed gateway.
3. Assert the log contains "Failed to sync slash commands" **and** the ready banner.
4. Assert `hasattr(bot, "_channel_settings_service")` is `False` and
   `DiscordBot._is_live_mode_enabled(bot, <any id>)` returns `False`.

## Acceptance criteria

- [ ] `ChannelSettingsService`, `UserPreferencesService` and `MessageVisibilityService` are
      constructed in `DiscordBot.__init__` next to the existing `PinService` at
      `discord_bot.py:364`, so their availability no longer depends on command registration.
- [ ] `register_personalization_commands` consumes them via `getattr(bot, ..., None) or ...`,
      matching the existing `_pin_service` idiom, so a fresh construction is still possible.
- [ ] A registrar failure sets a durable degraded marker on the bot.
- [ ] `get_service_health_status()` (`discord_bot.py:582-622`) reports the degraded state instead
      of hardcoding availability.
- [ ] The final log line is no longer an unconditional success banner when registration failed.
- [ ] The error message names *registration*, not *sync*, when the failure came from
      `setup_commands` rather than `tree.sync()`.
- [x] Full suite still green (the eager-construction change was prototyped at 125/125 against the
      `c83f740` suite; the gate is 401/401 now).

## Files to touch

- `src/bot/command_modules/personalization.py` — `:43`, `:146`, `:380` become

- `src/bot/commands.py:73-91` — optional: wrap each of the 11 registrar calls individually so a

  service coupling is removed.

a healthy status dict.

## Risks and notes

- **Existing tests:** `tests/test_command_registration.py:184-185` asserts `hasattr(bot,
  "_pin_service")` and `_message_visibility_service` after registration. Eager construction keeps
  those true, so they pass unchanged. The per-registrar isolation variant leaves
  `test_command_registration.py` unaffected because all registrars succeed there.
- Nothing asserts on the health-status dict today, so changing its shape breaks nothing — and that
  absence of coverage is itself worth a test.
- The two halves (eager construction; make-it-loud) are independent commits. If only one is done,
  do eager construction: it removes the whole class of invisible feature loss.
- Moving `setup_commands` into `setup_hook()` is a larger, better fix that also closes `DAB-003`
  (no re-entry guard) and `DAB-009`. It is out of scope here; note it in the commit message.
