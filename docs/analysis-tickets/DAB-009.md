# DAB-009: Unguarded `await change_presence()` sits before `setup_commands` in `on_ready`

- Type: BUG
- Severity / Payoff: S2 (recalibrated; owning lanes filed S3 / S2 / S3)
- Effort: XS
- Priority score: 6.0 — impact High (3) x frequency Rare (1) / effort XS (0.5)
- Confidence: **VERIFIED** (source inventory of every `await` in `on_ready`)
- Merged IDs: `B1-09`, `C2-07`, `C2-08`
- Blocks / Blocked by: blocked by `DAB-002` (do the eager-construction fix first; it turns this
  into a two-line change instead of a restructure). Collides with `DAB-002`'s presence-badge work —
  land them together.

## Context

`on_ready` guards `image_processing_service.start()` and `report_web_server.start()` with
`try/except`, and it guards `setup_commands` + `tree.sync()`. The single `await` sitting between
them — `await self.change_presence(activity=activity)` — is bare.

`Client.change_presence` writes to the gateway WebSocket. If the socket dropped between READY and
this call it raises `discord.ConnectionClosed`, `TypeError`, or an `aiohttp`/`websockets` error.
That exception escapes `on_ready` into `on_error`, so **`setup_commands`, `tree.sync()` and
`_start_automatic_rag_backlog` never run** — a strictly worse version of `DAB-002` in which *zero*
commands register and no service is attached.

Combined with `DAB-003` (no `on_ready` re-entry guard), the reconnect that would re-fire `on_ready`
raises `CommandAlreadyRegistered` instead, so the degradation cannot self-heal. Only a process
restart fixes it.

## Evidence

- Location: `src/bot/discord_bot.py:523-527`; the bare await is `:527`.
- Guarded neighbours: `image_processing_service.start()` at `:485-493`,
  `report_web_server.start()` at `:496-499`, `setup_commands` + `tree.sync()` at `:530-542`.
- Where the escaping exception lands: `on_error` at `:548-561`.
- Full `on_ready` body: `:461-546`.

**The reports give no line number for the `_start_automatic_rag_backlog` call site inside
`on_ready`.** It is known only to sit inside `:461-546` and after `:530-542`. The one line number
any report attaches to that function is `discord_bot.py:127-129`, which is the *method body's*
early-return guard, not the call site. Locate the call site before editing; do not copy a guessed
line number into the diff.

B1 probe output (`/tmp/b1probes/probe_b1_08_content_type.py`, second half) — an inventory of every
`await` in `on_ready`:

```
  line  486: await self.image_processing_service.start()      # inside try (:485-493)
  line  497: await self.report_web_server.start()             # inside try (:496-499)
  line  527: await self.change_presence(activity=activity)    # NOT guarded
  line  531: await setup_commands(self, self.config, self.gemini_client, self.perform
  line  534: synced = await self.tree.sync()
```

Trigger, verbatim: "a gateway close in the window between READY and the presence update (common
during Discord's rolling gateway restarts)."

Observable symptom: `Unhandled exception in event 'on_ready'` in the log; the bot connects but has
no slash commands and no live/personality/preferences services; recovery requires a reconnect that
re-fires `on_ready`, which then hits `DAB-003`.

## Reproduction

1. Patch `change_presence` to raise `discord.ConnectionClosed`.
2. Await `DiscordBot.on_ready()`.
3. Observe the exception escapes and `setup_commands` was never awaited.

## Acceptance criteria

- [ ] A `change_presence` failure is caught, logged at WARNING, and does **not** prevent
      `setup_commands`, `tree.sync()` or `_start_automatic_rag_backlog` from running.
- [ ] `_start_automatic_rag_backlog` is inside the protected region, so a gateway error at that
      point cannot skip command setup either.
- [ ] `on_ready` completes normally when presence fails.
- [ ] Full suite still passes.

## Files to touch

- `src/bot/discord_bot.py:523-527` — wrap in `try/except Exception` with a warning.
- `src/bot/discord_bot.py` — move the `_start_automatic_rag_backlog` call inside the guarded region
  (locate the line first; the reports do not give it).

Longer-term alternative, out of scope for this ticket but worth the commit message: move command
registration into discord.py's `setup_hook()`, which runs once before the first READY and whose
exceptions abort startup loudly instead of being swallowed. The two other repeated-startup steps
are already idempotent — `ImageProcessingService.start` (`image_processing_service.py:110-112`) and
`ReportWebServer.start` (`report_web_server.py:38-39`) both early-return — so `setup_commands` is
the odd one out.

## Test to add

`tests/test_discord_orchestration.py` (or `tests/test_bug_regressions.py`), an
`IsolatedAsyncioTestCase`:

```
test_presence_failure_does_not_skip_command_registration:
    patch change_presence to raise discord.ConnectionClosed
    patch tree.sync and _start_automatic_rag_backlog
    await bot.on_ready()
    assert setup_commands was awaited
    assert a WARNING naming change_presence was logged
```

If the defect returns, `setup_commands.assert_awaited()` fails.

Related test worth adding at the same time (covers `DAB-003`): call `on_ready()` twice against a
stubbed gateway and assert `setup_commands` was awaited exactly once and no error was logged.

## Risks and notes

- No existing test covers `on_ready`'s presence block; nothing is expected to break.
- `DAB-002`'s visibility work replaces this exact presence call with a degraded-status badge
  (status `idle` plus a "DEGRADED: ..." activity name). Both changes touch the same five lines.
  Land them as one commit or sequence them explicitly.
- Swallowing the presence error means the bot may show a stale or default presence. That is the
  correct trade: a wrong status badge is strictly better than zero registered commands.
