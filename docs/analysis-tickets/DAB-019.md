## Context

`LiveMessageCoordinator.run_channel_worker` pops the whole pending batch out of the dict **before**
processing it, then wraps processing in a bare `except Exception` that only logs. There is no
requeue, no retry counter, and no user-facing error. The batch is unreachable after the pop.

`process_messages` covers the entire expensive path — rate limiting, RAG retrieval, the Gemini
generation call, token recording, and delivery — so the loss window spans the whole multi-second
request.

The asymmetry is the tell. The non-live path surfaces failures through `_handle_response_error`.
Live mode *has* an error callback (`handle_response_error`) but invokes it only when
`api_response.success == False`, never for an exception.

## Evidence

- Location: `src/bot/live_message_coordinator.py:118-137` — pop at `:119`, bare log at `:127-137`.
- The Gemini generation call inside `process_messages`: `:309`.
- Delivery inside `process_messages`: `:330`.
- `handle_response_error` invoked only for `api_response.success == False`: `:320-324`.
- Sites that raise `RuntimeError` by design when the bot is partially constructed: `:308`, `:322`,
  `:329`.

The code as quoted by B2:

```python
async with lock:
    pending_messages = self.pending_messages.pop(channel_id, [])
...
try:
    response_sent = await self.process_messages(pending_messages)
except Exception as exc:
    logger.error("Live worker error in channel %s ...")   # nothing else
```

B2 probe (`/tmp/b2_probe_live.py` PROBE 3):

```

generate_response calls  : 1
pending after failure    : []
context buffer entries   : 0
```

plus the logged `Live worker error in channel 9 for messages 0-24: transient API 503`. **25 user
messages, one failed call, zero survivors, zero replies.**

Independent verification (V1, `/tmp/v1probes/p1_live_batch_loss.py`) reproduced it exactly:

```

VERDICT DATA: user notified = False
VERDICT DATA: retried = False
```

V1 also found the damning corroboration that this is an omission rather than a decision: the *same
file* requeues correctly 80 lines later when it deliberately splits a batch at an attachment
(`live_message_coordinator.py:216-220`):

```python
newly_queued = self.pending_messages.get(channel_id, [])
self.pending_messages[channel_id] = remaining_messages + newly_queued
```

The author knew the requeue idiom and did not apply it on the error path.

The existing `finally` at `:146-155` already re-checks `has_pending` under the lock and respawns
the worker, so a requeue in the `except` composes with machinery that is already there.

## Acceptance criteria

- [ ] When `process_messages` raises, the popped batch is re-queued **under the lock**, ahead of
      anything enqueued while it was in flight, so message order is preserved.
- [ ] A bounded attempt counter exists; after N attempts the batch is abandoned and the user is
      told, via `handle_response_error` against `messages[-1]`.
- [ ] Retries back off rather than spinning.
- [ ] The existing `finally` at `:146-155` restarts the worker automatically once the batch is back
      in `pending_messages` — verify this rather than adding a second restart path.
- [ ] A single transient failure results in the batch eventually being answered, not dropped.

## Risks and notes

- **Severity is contested.** An independent verification pass rated this **S3**, not S1, on three
  grounds: nothing durable is lost (the messages remain in Discord and were already written to the
  RAG index at `discord_bot.py:766-775`, which runs *before* the live-mode fork at `:778-780`); the
  channel is not left broken because the `finally` at `:146-155` restarts a worker; and the routine
  failure modes are already handled *inside* `process_messages`. Reaching the bare `except` requires
  an unexpected raise, e.g. a `discord.HTTPException` out of `send_response` at `:330`. The master
  register held S1 because a silently unanswered batch in the bot's flagship mention-free mode is
  invisible to the user and to the operator. Fix it either way; the fix is the same.
- A naive requeue can loop forever on a deterministic failure. The bounded attempt counter is not
  optional.
- Related latent hazard worth a comment, not a fix: if one of the injected callbacks were ever
  `None`, `:308`/`:322`/`:329` raise `RuntimeError` on **every** batch and live mode goes
  permanently, silently dead. The wiring at `discord_bot.py:163-188` uses
  `getattr(..., None)` against objects that do define them, so this is not currently reachable.
- Existing tests that build these coordinators: `tests/test_discord_orchestration.py` (11 tests via
  `make_coordinator(**overrides)` at `:33-48`), and `tests/test_bug_regressions.py:188-244`, which
  are the only callers of `_process_live_messages` and `_build_live_user_prompt`. Re-run both; none
  is expected to break.
