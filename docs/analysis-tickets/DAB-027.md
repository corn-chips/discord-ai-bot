# DAB-027: `_vector_lock` is held across CPU-bound numpy scoring, serialising all semantic retrieval

- Type: IMPROVEMENT
- Severity / Payoff: S2. **244x** concurrent throughput at 350k vectors (0.4 -> 97.5 ops/s at 16
  threads); scaling 1.10x -> 5.34x. The shipped lock delivers **literally zero** parallel speedup.
- Effort: M
- Priority score: 2.0 — impact Medium (2) x frequency Occasional (2) / effort M (2)
- Confidence: **VERIFIED** — concurrency measured at 1/2/4/8/16 threads with BLAS pinned to 1 thread
- Merged IDs: `B2-10`, `C5-04`; prototyped as `I3-02`
- Blocks / Blocked by: **blocks `DAB-028`** — the two were prototyped together and share the
  write-path atomicity risk. Land them as one change.

## Context

`MessageIndexService._vector_lock` is a process-global `threading.RLock` held across the *whole* of
`search_semantic` — masking, `np.flatnonzero`, the fancy-index gather, `np.linalg.norm`, the matmul,
`np.argsort`, and the Python list comprehension that builds `ranked`.

numpy releases the GIL for these operations, so the work is genuinely parallelisable. The lock
forbids it. `search_semantic_async` dispatches to `asyncio.to_thread`, so N concurrent requests land
on N pool threads and then queue on one lock.

## Acceptance criteria

- [ ] Readers take **no lock**. They rebind a published immutable tuple
      `(count, unit, ids, guilds, channels)` with a single attribute read, which is atomic under the
      GIL.
- [ ] Writers build the new tuple and swap it, under a **writer-side** lock (writers are already
      serialised).
- [ ] An O(n) rebuild per write is avoided: use capacity-doubling append with a version counter and
      rebuild only on compaction.
- [ ] `search_semantic` returns the **same message IDs in the same order** as before.
- [ ] Concurrency scaling at 4 threads is materially above 1.0x.
- [ ] The write path remains correct under a concurrent read — a reader holding a reference to the
      old tuple must see a consistent snapshot, never a torn one.

## Risks and notes

- **The real risk is write-path atomicity, not read correctness.** Under copy-on-write,
  `_cache_upsert`/`_cache_remove` must build a new tuple and rebind it — they can no longer mutate
  in place while a reader holds a reference. Writes are rare (one per embedded message) so an O(n)
  rebuild per write is too slow at 350k; the recommended shape is capacity-doubling append with a
  version counter, rebuilding only on compaction, keeping a writer-side lock. Readers stay
  lock-free.
- **Land with `DAB-028`.** They touch the same five methods, the payoff compounds (the lock-free
  snapshot is worth little while every call still copies 586 MiB), and shipping them separately
  means paying the write-path review twice.
- **Payoff scales with corpus size, which the target deployment does not maximise.** These numbers
  are at 200k-350k indexed messages; a hobbyist single-guild install is two to three orders of
  magnitude smaller. This sits in Tier 2 for that reason — it is correct, measured, and not urgent.
- `tests/test_rag_optimization.py:94` is the flaky timing test in this area. Expect it to be the
  first thing that moves when the locking changes; do not "fix" it by widening the window.
- `tests/test_message_rag_services.py` (21 tests) builds real temporary databases against these
  services and is the regression surface.
