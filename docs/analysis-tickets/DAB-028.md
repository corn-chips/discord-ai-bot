# DAB-028: `search_semantic` copies the whole matrix and recomputes norms on every call

- Type: IMPROVEMENT
- Severity / Payoff: S2. **2,225 ms -> 62 ms (35.8x)** and peak allocation **2,056 MiB -> 8.4 MiB**
  at 350k vectors; narrow-channel queries 5.94 -> 0.88 ms (6.8x). IDs and scores identical to 2e-6.
- Effort: M
- Priority score: 3.0 — impact Medium (2) x frequency Common (3) / effort M (2)
- Confidence: **VERIFIED** — five variants measured at 100k and 350k, equivalence checked
- Merged IDs: `B2-11`, `C5-05`; prototyped as `I3-03`
- Blocks / Blocked by: blocked by `DAB-027` — same locked region, same five methods, same
  write-path risk. Land them together.

## Context

Inside the vector lock, `search_semantic` materialises a full copy of the selected rows and
recomputes L2 norms that never change:

```python
matrix = self._vector_matrix[positions]      # fancy index == full copy
norms  = np.linalg.norm(matrix, axis=1)      # recomputed every search
scores[valid] = (matrix[valid] @ query_vector) / (norms[valid] * query_norm)
```

`positions` from `np.flatnonzero` is an integer array, so `self._vector_matrix[positions]`
materialises a brand-new N x 768 array — **586 MiB at 200k vectors** — on every query, and then
`matrix[valid]` copies it *again*. Row norms are recomputed from scratch even though the vectors are
immutable once stored. All of it happens inside the global lock.

## Acceptance criteria

- [ ] Vectors are stored **L2-normalised** at load/upsert time, so cosine becomes a plain dot
      product with no per-call `norm`.
- [ ] Unit vectors **replace** the raw matrix rather than sitting alongside it (see Risks).
- [ ] Scoring uses one contiguous BLAS matvec over the whole matrix with masking applied *after*,
      instead of gathering `matrix[positions]` — eliminating the copy.
- [ ] Top-k uses `argpartition` plus a threshold fix-up rather than a full `argsort`, and preserves
      exact tie-breaking.
- [ ] The path is **adaptive**: gather when the selection is <= 10% of rows, whole-matrix matvec
      otherwise. Neither query shape regresses.
- [ ] Returned message IDs are in the same order as before and scores agree to < 2e-6.
- [ ] Peak allocation per query is single-digit MiB, not hundreds.

## Risks and notes

- **Tie-breaking is load-bearing.** `_exact_topk` must deliberately reproduce
  `np.argsort(-scores, kind="stable")[:limit]`, including tie-breaking by ascending index —
  necessary because duplicate Discord messages produce identical embeddings and therefore exact
  score ties. Get this wrong and rankings shuffle non-deterministically.
- **Storing unit vectors must replace the raw matrix, not sit alongside it.** Measured at 350k:
  raw f32 + 3 id arrays = 1028.3 MiB (3,081 B/msg, matching the independently measured 3,096 B/msg);
  keeping raw *and* unit = 6,153 B/msg. The raw vectors are already durable in SQLite, so the cache
  only needs unit vectors — **zero net memory change**.
- **float16 was measured and rejected.** Half the memory, **20x slower**: numpy has no float16 GEMM,
  so it upcasts element-wise outside BLAS.

  | dtype | matrix | search @350k | recall@12 |
  |---|---|---|---|
  | f32 unit | 1025 MiB | **60.17 ms** | 1.000 |
  | f16 unit | **513 MiB** | **1214.24 ms** | 0.997 |

  int8 with explicit int32 accumulation could work but needs a hand-written kernel — out of scope.
- **The 10% adaptive threshold should be re-tuned per deployment.** It was derived from the measured
  crossover at 100k (gather ~2.2 us/row vs a fixed ~26 ms full matvec). At the target deployment's
  corpus size the gather branch will essentially always win.
- Inherits `DAB-027`'s write-path atomicity risk if landed together, which it should be.
- **Payoff scales with corpus size.** At a hobbyist single-guild scale these numbers are milliseconds
  either way. This is Tier 2 because it is correct and measured, not because it is urgent.
