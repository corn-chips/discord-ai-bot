# DAB-029: Six in-memory containers never evict

**Status: PARTIAL** — item **5a only**, landed in round 2 Phase 5: the completed-job archive no longer retains `request.image_data`. **Five of the six containers are untouched** (1-2, 3, 4, 5b, 6); do not read this as DAB-029 closed. Two corrections found by executing the prescription: `dataclasses.replace(job.request, image_data=b"")` raises `ValueError` from `__post_init__`, and `result.edited_image` must NOT be dropped at archive time because `/edit-image` reads it back from the archive.

- Type: IMPROVEMENT
- Severity / Payoff: S2. Measured on the worst one: **699.5 MiB -> 1.9 MiB (373x)** at 3.5 us/job.
  The others: 18.31 KiB per saturated live channel, 3096 B/message of vector cache, 1185 B per
  pregenerated channel, 218 B per image-service user.
- Effort: S
- Priority score: 6.0 — impact Medium (2) x frequency Common (3) / effort S (1)
- Confidence: **VERIFIED** — each container measured with `tracemalloc` or `/proc/self/statm`
- Merged IDs: `B2-01`, `B2-12`, `B2-13`, `B2-19`, `B2-20`, `B4-21`, `C5-19`; prototyped as `I3-14`
  and `I3-15`
- Blocks / Blocked by: none. This is one cluster because it is one policy decision — every one of
  them needs a bound and an eviction rule.

## Context

Six independent get-or-create containers with no eviction and no cleanup in `close()`. They differ
only in what they leak.

| # | Container | Location | Measured retention |
|---|---|---|---|
| 1 | `LiveMessageCoordinator.locks` | `live_message_coordinator.py:67-68`, `:71-77` | 5,000 entries after 5,000 channels |
| 2 | `LiveMessageCoordinator.context` | `live_message_coordinator.py:67-68`, `:79-85` | **18.31 KiB per saturated channel** |
| 3 | vector cache | `message_index_service.py:767-781`, `:724-737` | 3,096 B/msg; 1M msgs -> ~2,930 MiB |
| 4 | `_pregeneration_status` | `hybrid_context_retriever.py:63`, `:197-204`, `:346`, `:412-431` | 1,185 B per channel, forever |
| 5 | `_completed_jobs` payloads | `image_processing_service.py:81`, `:465-469`, `:288-292`, `:182-183`, `:614-640` | **700 MiB for 100 jobs** |
| 6 | `_user_rate_limits` | `image_processing_service.py:86`, `:526-544` | 218 B/user x 200,000 = 41.6 MiB |

Container 5 is the one to fix first and the one with a prototyped policy.

## Evidence

**1 and 2 — live-mode `locks` / `context`.** `get_channel_lock` and `get_context_buffer` are pure
get-or-create keyed by `channel_id`. Nothing ever deletes a key. `self.tasks` and
`self.pending_messages` *are* popped when a worker drains, but `locks` and `context` are not, and
`close()` (`:157-172`) clears only `pending_messages` and `tasks`. Each context value is a
`deque(maxlen=turn_window * 2)` (12 by default) of `MessageContext` objects whose `content` is
truncated to 1200 chars (`:188-189`). Deleting the Discord channel or disabling live mode does not
release it. The backing dicts are handed in at `discord_bot.py:433-436`.

```
channels driven          : 5000
len(coord.locks)         : 5000
len(coord.context)       : 5000
len(coord.tasks)         : 0  (workers exit -> popped)
tracemalloc delta        : 8009.8 KiB (1640.4 bytes/channel retained)

channels=2000 locks=2000 ctx=2000 buffer_len=12
retained=35.77 MiB -> 18.31 KiB per live channel (saturated)
projection: 1,000 channels = 17.9 MiB, 10,000 channels = 178.8 MiB
```

**3 — the vector cache.** On the first semantic search, `_load_vector_cache` `SELECT`s **every**
`done` embedding and holds them for the process lifetime. `_ensure_vector_capacity` doubles the
arrays, so peak RSS during growth is ~2x steady state. The full-table SELECT and decode loop run
*inside* `with self._vector_lock`, so the first search after startup blocks every other reader and
writer for the duration.

```
   10,000 embeddings ->     29.5 MiB resident (3096 B/msg)
  100,000 embeddings ->    295.3 MiB resident
  500,000 embeddings ->  1476.3 MiB resident
  projection: 1,000,000 indexed messages -> ~2,930 MiB of float32 matrix
```

**4 — `_pregeneration_status`.** Every `start_channel_pregeneration` writes a 6-key status dict
keyed by channel and nothing ever removes it. `_pregeneration_tasks` *is* popped in the `finally` at
`:346`, and `cancel_background_work` pops tasks too (`:393-400`) — but it walks
`_pregeneration_status.values()` to *mutate* phases (`:395-403`) rather than to delete them.

```
channels pregenerated    : 20000
len(_pregeneration_tasks): 0  (popped, ok)
len(_pregeneration_status): 20000  <- never pruned
retained                 : 22.60 MiB (1185 B per channel, forever)
after close(), status len: 20000 (close() clears tasks at :429-431 but NOT status)
```

Also a correctness smell: `get_pregeneration_status` will happily return a `phase="complete"` record
from days ago.

**5 — `_completed_jobs` payloads.** The count *is* capped at 100 in all three append paths
(`:183-184`, `:291-292`, `:479-480`) with an hourly age cleanup (`:638-641`). **The defect is
payload retention, not an unbounded count.** Each retained `ProcessingJob` holds
`request.image_data` (the full uploaded image) *and* `result.edited_image` (the full generated
image). Only `.result` is ever read back (`get_job_status` fallback at `:250-254`), so the request
payload is pure ballast. The hourly cleanup only drops jobs older than one hour, so a burst pins the
full 100 for up to an hour.

```
jobs retained            : 100 (hard cap 100)
resident bytes           : 700 MiB for 4 MiB in + 3 MiB out
worst case at config max_image_size_mb=10 -> ~2000 MiB held
```

Bounded alternative measured:

| | measured |
|---|---|
| 350 completed jobs x 2 MiB image | **699.5 MiB** |
| **LRU cap 64 + 15-min TTL + drop the payload on completion** | **1.9 MiB (373x less)** |
| cost of the bounded `add()` | **3.51 us/job** |

**6 — `_user_rate_limits`.** Expired timestamps are pruned only for the *calling* user
(`user_requests[:] = [...]`), and the key is never deleted even when the list becomes empty. A user
who makes exactly one image request keeps a dict key and a list object for the process lifetime.

```
distinct users           : 200000
len(_user_rate_limits)   : 200000  <- never GC'd
retained                 : 41.6 MiB (218 B/user)
```

## Acceptance criteria

Ordered by value. Container 5's first item is most of the payoff.

- [ ] **5a.** On completion, the request payload is stripped before archiving:
      `job.request = dataclasses.replace(job.request, image_data=b"")` (or store a lightweight
      `CompletedJobRecord` with just `job_id`, `status`, `error_message`, timings and `result`).
      `result.edited_image` is dropped once delivered.
- [ ] **5b.** The archive is capped by **bytes** as well as count (cap 64 / TTL 15 min measured).
- [ ] **6.** `if not user_requests: del self._user_rate_limits[user_id]` after pruning, plus an
      amortised sweep folded into the existing hourly `_periodic_cleanup`.
- [ ] **1-2.** Per-channel state is evicted on idleness: record `last_used`, sweep entries older
      than a TTL from the worker's `finally`, drop the lock entry when `tasks`,
      `pending_messages` and the context buffer are all empty. `close()` clears `locks` and
      `context`.
- [ ] **4.** `_pregeneration_status` becomes an `OrderedDict` capped at ~256 entries with
      `popitem(last=False)` eviction of terminal (`complete`/`failed`/`cancelled`) records, carries
      a `finished_at`, and is cleared in `close()`.
- [ ] **3.** A configurable cap (`rag_vector_cache_max_vectors`) with recency-based eviction; rows
      loaded **outside** the lock and swapped in under it; the loaded vector count and estimated
      bytes logged at startup so the growth is observable.

## Risks and notes

- **Do not write "retained forever" for `_completed_jobs`.** One source characterises it that way;
  the shipped code hard-caps the count at 100 and cleans hourly. The defect is payload retention.
  The 699.5 MiB figure is a synthetic 350-job model; the real measured figure is 700 MiB for the
  100-job cap with 4 MiB in / 3 MiB out. Both are large; only one is accurate about the mechanism.
- **The router cache is NOT part of this cluster, despite appearing in some summaries.** It is
  already an `OrderedDict` LRU with TTL: `enhanced_command_handler.py:70-72` (construction),
  `:103-107` (TTL expiry + `move_to_end`), `:119-120` (LRU trim), defaults
  `router_cache_size: 256` / `router_cache_ttl: 300` (`config.yaml:83-84`,
  `src/config.py:107-108`, parsed at `src/config_helpers.py:176-181`, validated positive at
  `:602-605`). The quoted "96.2 MiB -> 0.0 MiB" measures a hypothetical unbounded 200k-entry dict,
  not shipped behaviour. **File it as verify-and-close, or add a regression test pinning the trim at
  `:119-120`. Do not file it as an unbounded-growth bug.**
- **Behaviour change on container 5:** a user polling a job ID older than the TTL gets "not found"
  instead of a cached result. Cap 64 / TTL 15 min is generous relative to any realistic poll window,
  but it is a user-visible change — say so in the response text.
- **Container 3 overlaps `DAB-028`.** The unboundedness is here; the per-call matrix copy is a
  separate fix and lives there. Do not conflate them.
- No existing test names any of these as breaking; every finding proposes a **new** test. Adjacent
  suites to re-run: `tests/test_discord_orchestration.py` (11 coordinator tests),
  `tests/test_message_rag_services.py` (24), `tests/test_sqlite_services.py` (10).
- The six can be landed independently. Do 5a first — it is one line and 373x.
