# DAB-032: The rate limiter rebuilds every active user's history on every call, on the event loop

**Status: OPEN** — and now with a second instance to fix: `b9a4514` added `expensive_command_limiter`, which has the same O(n) rebuild.

- Type: IMPROVEMENT
- Severity / Payoff: S3. **p95 22.119 ms -> 0.003 ms at 20,000 tracked users (6,320x)**
- Effort: S — ~30 LOC in one file
- Priority score: 4.0 — impact Low (1) x frequency Continuous (4) / effort S (1)
- Confidence: **VERIFIED** — measured at four scales
- Merged IDs: `B2-16`, `C5-08`; prototyped as `I3-09`
- Blocks / Blocked by: none

## Context

Each `check_and_record` walks the *entire* `_requests` map — `list(...items())` plus a list
comprehension per user — before touching the caller's own bucket. Cost is O(total tracked users x
timestamps per user) per request, all on the single event-loop thread. The `asyncio.Lock` yields
nothing to other work here because the body has no awaits.

State itself **is** bounded (users with no entry in the last hour are deleted), so this is a CPU
problem, not a leak.

## Evidence

Location: `src/services/rate_limiter.py:23-31`, inside `TextRateLimiter.check_and_record`
(`def` at `:17`). The clock reads are at `:19-21`; the delete is at `:30`.

> Note: some sources cite `rate_limiter.py:24-30` and some cite the bare filename with no
> directory. The file is `src/services/rate_limiter.py` (there is no `src/utils/rate_limiter.py`),
> and `:23-31` is the block.

```python
    async def check_and_record(self, user_id: int) -> tuple[bool, Optional[str]]:
        """Validate and record a request for the given user."""
        now = datetime.now(timezone.utc)                                    # :19
        minute_cutoff = now - timedelta(minutes=1)                          # :20
        hour_cutoff = now - timedelta(hours=1)                              # :21

        async with self._lock:                                              # :23
            # Prune expired entries for all users to prevent unbounded growth.
            for existing_user_id, timestamps in list(self._requests.items()):   # :25
                recent = [ts for ts in timestamps if ts >= hour_cutoff]     # :26
                if recent:
                    self._requests[existing_user_id] = recent               # :28
                else:
                    del self._requests[existing_user_id]                    # :30

            requests = self._requests.get(user_id, [])                      # :32
```

Measured (`/tmp/b2_probe_ratelimit.py` PROBE 15):

```

len(_requests)           : 84                     <- bounded, prune works
retained                 : 0.05 MiB (600 B per live user)
one check_and_record with 20000 live users: 27.01 ms (blocks the event loop)
```

Memory side-note from the same prototype: `_requests` at 20k users x 6 timestamps is 6.5 MiB; a
deque halves it.

A related nit worth folding in: `now`, `minute_cutoff` and `hour_cutoff` are computed *before* the
lock is acquired (`:19-21`), so under contention the recorded timestamp is slightly stale — harmless,
but it makes the window marginally generous.

## Acceptance criteria

- [ ] `check_and_record` prunes only the **caller's** bucket on the hot path.
- [ ] The global sweep is amortised — once per 60 s, or every N calls — and still deletes users idle
      for more than an hour.
- [ ] Per-user storage becomes a `deque`, so expiry is a bounded `popleft` loop that is O(expired)
      rather than O(all).
- [ ] The minute count uses a reverse scan that stops at `per_minute`.
- [ ] **Admit/deny decisions are unchanged** for every input.
- [ ] The retry-after message text is unchanged. The shipped code uses `min(...)` at
      `src/services/rate_limiter.py:37`; the deque's head is the same value.
- [ ] One `check_and_record` with 20,000 live users completes in microseconds.

## Risks and notes

- **This is Tier 0 on cheapness, not on urgency.** At the target deployment's scale — one guild, a
  handful of friends — `_requests` holds tens of entries and the current cost is microseconds. The
  measured 22 ms p95 is at 20,000 tracked users. It is on the list because it is 30 lines and it
  runs on `on_message`, which is the hottest path in the bot.
- The whole module has **zero** test coverage. Writing the first test file is arguably more valuable
  than the optimisation itself.
- The only behavioural surface to preserve is the retry-after message text. Verify by asserting the
  exact string for a denied request before and after.
- Contrast worth noting while you are in the area: `image_processing_service.py:526-544` does the
  opposite — it prunes only the calling user and never deletes the empty key, which is `DAB-029`
  container 6. One file over-prunes, the other under-prunes.
- No existing test breaks; there is nothing to break.
