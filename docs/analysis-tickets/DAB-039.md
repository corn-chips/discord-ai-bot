# DAB-039: `_get_response_text` fallback ignores `part.thought`, posting chain-of-thought to Discord as the answer

**Status: LANDED** in `7955652` — the `_get_response_text` fallback now honours `part.thought`, so private reasoning cannot be returned as the answer.

- Type: BUG
- Severity / Payoff: **S1** (recalibrated; B3 filed S1. An independent verification pass argued S4
  because the trigger is unreachable at HEAD — see Risks)
- Effort: XS (a two-line guard)
- Priority score: 8.0 — impact Critical (4) x frequency Rare (1) / effort XS (0.5)
- Confidence: **VERIFIED** mechanism; **THEORETICAL** trigger at HEAD
- Merged IDs: `B3-17`
- Blocks / Blocked by: none. Shares a root cause with `DAB-048` (thinking tokens never billed):
  the codebase does not model thought parts at all.

## Context

`GeminiClient._get_response_text` first tries `response.text`, and if that is falsy it walks
`candidate.content.parts` and returns the first part that has `.text`. The SDK's own `.text`
property deliberately **skips** thought parts. The hand-rolled fallback does not.

So `response.text` is `None` exactly when the only text present is chain-of-thought — and that is
precisely the case in which the fallback fires and returns the thought text. The fallback was
presumably written to work around an SDK quirk; it instead defeats the SDK's redaction.

The realistic path is `finish_reason = MAX_TOKENS`, where the thinking budget consumed the whole
output cap before any answer token was emitted. That reaches the user framed as a legitimate
answer, complete with the truncation footer.

## Evidence

- Location: `src/services/gemini_client.py:1529-1555`; the offending loop is `:1549-1551`.
- Consumers: `:1105` (finish_reason STOP) and `:1116` (MAX_TOKENS).

The defective code as quoted by B3:

```python
if hasattr(response, 'text') and response.text:
    return response.text
if hasattr(response, 'candidates') and response.candidates:
    candidate = response.candidates[0]
    ...
    for part in candidate.content.parts:
        if hasattr(part, 'text') and part.text:
            return part.text          # no part.thought check
```

The SDK contract it defeats (`GenerateContentResponse._get_text` in `google-genai` 2.11.0):

```python
if isinstance(part.text, str):
    if isinstance(part.thought, bool) and part.thought:
        continue
```

B3 probe 1 (`/tmp/b3_probe_thoughts_leak.py`), STOP case:


Independent verification (V1) reproduced the asymmetry exactly:

```

                       system prompt. Step 1: ...'
```

## Reproduction

Construct a real `google.genai.types.GenerateContentResponse` whose single content part has
`thought=True` and non-empty `.text`, then call `GeminiClient._get_response_text(response)`. It
returns the thought text; `response.text` returns `None`.

Both probes build a real `BotConfig` from the repo's real `config.yaml` and a `GeminiClient` via
`object.__new__`, so `genai.Client()` is never constructed — no credentials, no network.

## Acceptance criteria

- [ ] `_get_response_text` returns `None` for a response whose only text parts are thought parts,
      for both `STOP` and `MAX_TOKENS`.
- [ ] `_interpret_provider_response` then reports `success=False` (routing to the existing
      `max_tokens` / empty-response handling) rather than delivering the thought text.
- [ ] Ordinary responses with a mix of thought and answer parts return the **answer**.
- [ ] No thought text can reach `message.reply`.

## Files to touch

- `src/services/gemini_client.py` — `_get_response_text` at `:1529-1555`, loop `:1549-1551`:

```python
for part in candidate.content.parts:
    if getattr(part, "thought", False):
        continue
    if getattr(part, "text", None):
        return part.text
```

B3's stronger recommendation: delete the fallback entirely and trust `response.text`. If it is
`None`, that is a genuine empty response and the caller's existing `None` -> retry / `max_tokens`
error handling is the right outcome.

- Optional, same theme: raise `max_output_tokens_low` above the thinking budget, or set
  `include_thoughts=False` explicitly. `max_output_tokens_low` is currently `4096`; no
  `config.yaml` line number is given in the source reports for that key.

## Risks and notes

- **The trigger does not exist at HEAD, and that is why severity is contested.** An independent
  verification pass searched the repo for `include_thoughts` and `thoughts`
  (`grep -rn "include_thoughts\|thoughts" --include=*.py --include=*.yaml .`, `.venv` excluded) and
  found **zero hits**. `_build_thinking_config_for_model` (`gemini_client.py:575-620`) only ever
  sets `thinking_level=` or `thinking_budget=`, and `types.ThinkingConfig()` defaults
  `include_thoughts=None`. Gemini returns thought parts only when `include_thoughts` is true. That
  pass rated the finding **S4-Trivial (latent; becomes S2 the day thought summaries are enabled)**.
  It also flagged its own reasoning as `UNPROVABLE-HERE`: "the API never returns thought parts
  unless `include_thoughts=True`" was verified against the SDK's contract and documented semantics,
  not against a live call.
- The master register held **S1** because the consequence is a direct disclosure of the model's
  internal reasoning about the user, under the bot's normal model header, and the fix is two lines.
  Treat it as a two-line insurance policy rather than an emergency.
- No existing test is named as breaking. Baseline was 125 tests OK at `c83f740`; the gate is 401.
- If you take B3's stronger option (delete the fallback), verify the `MAX_TOKENS` consumer at
  `:1116` still produces the truncation message rather than a hard error.
