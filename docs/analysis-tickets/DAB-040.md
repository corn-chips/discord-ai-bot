# DAB-040: Retry classification is substring matching on `str(error)`; real 429s are never retried and bare digits false-positive as 5xx

- Type: BUG
- Severity / Payoff: S2 (recalibrated; B3 filed S1, B8 filed S3)
- Effort: S
- Priority score: 9.0 — impact High (3) x frequency Common (3) / effort S (1)
- Confidence: **VERIFIED** — reproduced by two lanes and again during reconciliation, using real
  `google.genai` error objects
- Merged IDs: `B3-04`, `B8-14`
- Blocks / Blocked by: blocked by `DAB-041` (same function; land the one-line class dispatch first)

## Context

`ErrorManager.categorize_error` classifies exclusively by `term in str(error).lower()`, walking a
fixed ordered `elif` chain. Two structural problems:

**Under-matching.** `google.genai.errors.APIError.__str__` is `f'{code} {status}. {details}'`. A
real Gemini quota rejection reads
`429 RESOURCE_EXHAUSTED. {... 'You exceeded your current quota ...' ...}`. The rate-limit term list
is `["rate limit", "quota exceeded", "too many requests"]`. `"You exceeded your current quota"`
does not contain the contiguous string `"quota exceeded"`; the help URL says `rate-limits`, not
`rate limit`; `429` is in no list. Result: `UNKNOWN_ERROR`, not retryable. **The single most common
transient Gemini failure is never retried.**

**Over-matching.** The 5xx list contains the bare substrings `"503"`, `"502"`, `"500"` and is
checked **before** the 400 list. Any message containing those digits anywhere — "exceeds the
maximum of 1500 characters" — is classified `SERVICE_UNAVAILABLE` and retried four times even
though it is a permanent client error.

## Acceptance criteria

- [ ] A real Gemini 429 (`code=429` / `status="RESOURCE_EXHAUSTED"`) classifies as `RATE_LIMIT` and
      `should_retry` is `True`.
- [ ] `"Response exceeded 1500 characters"` no longer classifies as `SERVICE_UNAVAILABLE` and is
      not retried.
- [ ] `403` / `PERMISSION_DENIED` classifies as `AUTHENTICATION_ERROR`.
- [ ] `404` classifies as `INVALID_REQUEST`.
- [ ] No realistic in-house message containing an incidental `400`/`500`/`502`/`503` substring is
      classified from that substring alone.
- [ ] The substring chain remains only as a last-resort fallback, with word-boundary anchoring.

## Files to touch

- `src/utils/error_manager.py` — `categorize_error` `:170-241` (branches at `:194`, `:216-227`,
  `:222`, `:226`, `:230`, `:232`, `:236`, fallthrough `:241`); retryable set `:265-276`.

B3's recommended first pass, ahead of the substring chain:

```python
code = getattr(error, "code", None)            # google.genai APIError / ClientError / ServerError
status = str(getattr(error, "status", "") or "").upper()
if code == 429 or status in {"RESOURCE_EXHAUSTED"}:      return ErrorType.RATE_LIMIT
if code in (500, 502, 503, 504) or status in {"UNAVAILABLE", "INTERNAL", "DEADLINE_EXCEEDED"}:
                                                          return ErrorType.SERVICE_UNAVAILABLE
if code in (401, 403) or status in {"UNAUTHENTICATED", "PERMISSION_DENIED"}:
                                                          return ErrorType.AUTHENTICATION_ERROR
if code in (400, 404) or status in {"INVALID_ARGUMENT", "NOT_FOUND", "FAILED_PRECONDITION"}:
                                                          return ErrorType.INVALID_REQUEST
```

Plus the `isinstance` pass from `DAB-041`. Then keep the substring chain as a last resort, replacing
the bare `"500"/"502"/"503"` tokens with an anchored regex:
`re.search(r"\b(?:HTTP\s*)?50[023]\b", error_str)`.

def test_numeric_substrings_do_not_false_positive(self):
    for msg in ("Message exceeds 4000 characters", "Retrieved 2400 candidate messages",
                "Response was 1500 tokens over budget"):
        self.assertIs(em.categorize_error(Exception(msg)), ErrorType.UNKNOWN_ERROR)

## Risks and notes

- **No existing test breaks.** `categorize_error` has zero behavioural coverage today.
- Making real 429s retryable increases the number of retries the bot actually performs. Pair with
  `DAB-042` (whole-sequence deadline) and `DAB-043` (uncapped server-suggested `retry_after`) or
  the bot can now legitimately spend 488 s on one message where before it failed fast.
- Fixing the `"invalid format"` ordering collision at `:194` vs `:232` is `DAB-176`; it is one line
  and belongs in the same commit series.
- Do not reorder the `elif` chain without re-running the full 19-case table; the ordering is
  load-bearing in ways that are not obvious from reading it.
