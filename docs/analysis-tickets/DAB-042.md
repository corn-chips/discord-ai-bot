# DAB-042: No whole-sequence deadline; one Discord message can occupy the bot for ~488 seconds

**Status: PARTIAL — the B3-03 third has LANDED (round 2, Phase 1); the whole-sequence deadline has not.** DAB-204 is also discharged, so the deadline is unblocked whenever it is taken up.

**What landed.** Backoff now happens on *every* retry decision. It used to live inside
`_handle_response_exception`, which covered exactly one of the loop's three paths; the empty-STOP
fall-through and the timeout branch both went straight round again with no delay. The empty-STOP
case was the expensive one — measured at **four fully billed provider calls in 0.0001 s**, images
and the whole assembled context included, ending in a generic `unknown_error`. That is a live 4x
cost multiplier with a real trigger, as against a latency ceiling with a theoretical one, which is
why it was split out and landed first. `_handle_response_exception` now returns
`(final_response, retry_delay)` and the caller owns the sleep. Guarded by
`test_an_empty_stop_response_backs_off_before_each_retry` and `M-DAB042A`.

**What did not land, and is still worth doing:** the whole-sequence deadline itself, the
`retry_after` cap (`min(suggested, 30.0)`, abandoning the retry when the delay exceeds the
remaining budget), and a distinct `empty_stop` error type so the four-attempt exhaustion stops
reporting itself as `unknown_error`.

Three things to know before implementing, each established by execution:

- **Put the budget inside `GeminiClient._run_response_attempts`, not in `response_generation.py`.**
  Only there can it shorten each attempt and still return a structured `timeout` error; an outer
  wrapper can only cancel, which discards the structured error and leaves
  `response_generation.py:402` reporting the *per-attempt* figure — a lie the moment a total budget
  exists. It is also what dissolves the acceptance-criteria contradiction below.
- **This ticket's acceptance criterion contradicts DAB-204's.** Lines 117-119 here require *fewer
  than* `max_retries + 1` attempts under a short budget; DAB-204 line 142 requires every observed
  deadline to be `>= per_attempt x (max_retries + 1)`. Both are satisfiable only with the budget
  inside the client, where DAB-204's guard observes nothing and is vacuously satisfied.
- **The 488 s figure is the tail, not the mode**, and two adjacent findings outrank it. The
  per-attempt budget is 120 s only for router-classified `medium`/`high`; `low` is 4 x 30 = 120 s
  in total. Text generation is genuinely non-blocking (measured: a second user was served at
  t = 0.001 s while the first hung). What is *not* non-blocking is the router at
  `enhanced_command_handler.py:189`, an untimed `asyncio.to_thread` on the shared default executor,
  which stalls every SQLite call in the process. And the empty-STOP retry branch fires **four
  billed provider calls in 0.0001 s** with zero backoff. Both are round-2 Phase 1 work, and neither
  needs this deadline.

- Severity / Payoff: S2
- Effort: M

- Confidence: **VERIFIED** by a virtual-clock probe

## Context

`_run_response_attempts` loops `max_retries + 1 = 4` times. Each iteration wraps the provider call
in `asyncio.wait_for(..., timeout=plan.timeout_duration)`. That timeout is **per attempt**. Nothing
tracks cumulative elapsed time, and no caller wraps `generate_response` in a deadline. The budget is
therefore multiplied by the attempt count.

Two sibling defects compound it:

- **`B3-03`** — backoff is applied only on the exception path. The timeout branch and the
  empty-STOP branch retry with **zero** delay. An empty-STOP response usually returns fast, so the
  bot fires four full requests — including all images and the entire formatted context —
  back-to-back within milliseconds.
- **`B3-02`** — a server-suggested `retry_after` is honoured verbatim and uncapped, producing a
  three-hour stall in the unbounded variant.

| Every attempt burns the budget then raises a retryable 5xx | `4 x 120 + (2^0+2^1+2^2) + 3 jitters` | **487.3 - 488.5** |

then goes silent for up to eight minutes before replying "Request Timeout". Meanwhile the user's
rate-limit slot is consumed, `message.channel.typing()` is held open, and the status message stays
on screen.

## Acceptance criteria

- [ ] A request-level deadline exists: `deadline = time.monotonic() + config.response.total_timeout`
      captured once in `_run_response_attempts`.
- [ ] Each attempt's timeout is `min(plan.timeout_duration, deadline - time.monotonic())`.
- [ ] The loop breaks with the `timeout` error response when the remaining budget is non-positive,
      so fewer than `max_retries + 1` attempts run when the budget is smaller than
      `(max_retries + 1) x per_attempt`.
- [ ] Backoff is applied on **every** retry decision, not only the exception path. The timeout and
      empty-STOP branches sleep too.
- [ ] `retry_after` is capped: `min(error_context.retry_after or backoff(attempt), MAX_BACKOFF)`
      with `MAX_BACKOFF = 30.0`, and a suggested delay exceeding the remaining budget abandons the
      retry immediately rather than sleeping.
- [ ] The empty-STOP branch gets its own error type (`empty_stop`) instead of falling through to
      `unknown_error` at `:1313`.
- [ ] The budget is a **new** config key carried through all four places. `api_timeout_buffer` was
      deleted in `9894bcc` — its `config.yaml` key, its `BotConfig` field and its
      `src/config_helpers.py` parser are all gone, and the lines once cited for it
      (`config.yaml:61`, `src/config.py:78`, `src/config_helpers.py:244-245`) now hold
      `response.max_retries`. There is nothing left to wire in or delete.

## Test to add

`tests/test_gemini_pipeline.py`:

```
test_total_budget_bounds_the_retry_sequence:
    patch gemini_client.asyncio.wait_for to raise asyncio.TimeoutError immediately,
      recording the timeout= value it was handed
    assert the recorded timeouts are strictly decreasing
    assert their sum never exceeds the configured total budget
    assert fewer than max_retries+1 attempts run when the budget is smaller than
      (max_retries+1) x per_attempt
```

Plus three backoff cases, each patching `asyncio.sleep` with an `AsyncMock`: (a) all attempts time
out, (b) all attempts return STOP with empty text, (c) all attempts raise a retryable error. Assert
`sleep.await_count == max_retries` in **all three** and that the delays are non-decreasing.

Plus the cap: feed an exception whose message contains `retry after 3600` and assert every recorded
delay is `<= 30.0`.

If the defect returns, case (a) and case (b) both report `sleep.await_count == 0`.

## Risks and notes

- **`tests/test_bug_regressions.py:110`
  `test_main_response_path_does_not_wrap_client_retry_timeout` FAILS a correct implementation of
  this fix.** It patches `src.bot.discord_bot.asyncio.wait_for` with
  `side_effect=AssertionError("outer wait_for must not own Gemini retries")`, and because
  `src.bot.discord_bot.asyncio` *is* the singleton `asyncio` module, that patch is effectively
  global. A mutation implementing exactly the fix above was run against a `/tmp` copy and the test
  **failed**. Worse, the failure surfaces as a misleading `TypeError: object Mock can't be used in
  'await' expression` because `response_generation.py:488`'s blanket `except Exception` swallows the
  `AssertionError`. **Rewrite that test first — that is `DAB-204`.**
- The same test is **blind** to the modern idiom: a mutation reintroducing the bug via
  `async with asyncio.timeout(...)` passes it. Whatever replaces it must assert the *budget*, not a
  call name.
- Landing this without `DAB-040`/`DAB-041` means the deadline mostly protects paths that currently
  fail fast anyway. Landing `DAB-040` without this means the bot legitimately retries more often
  against an unbounded budget. Sequence them: `DAB-041` -> `DAB-204` -> `DAB-040` -> this.
- `B3-02`'s trigger is marked **THEORETICAL**: current `google-genai` 429s serialise the delay as
  `retryDelay: '54s'`, which does not match the parser's wording. The value is nonetheless
  upstream-controlled, and `handle_image_processing_error` hard-codes `retry_after = 120` for
  `ErrorType.NANO_BANANA_API_ERROR`, which is reachable today.
