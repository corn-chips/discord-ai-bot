# DAB-065: A transient DB error during a message edit permanently tombstones the message

> **DONE — landed in Phase 4, and NOT by the route the acceptance criteria describe.**
>
> The `ON CONFLICT ... deleted_at = NULL` fix is wrong twice: it reintroduces BUG-0004 (see
> `ANALYSIS_CORRECTIONS.md` item 4) **and it would not have worked** — `mark_deleted` also sets
> `hidden = 1`, which independently removes the row from FTS and all three retrieval paths.
> Measured: clearing `deleted_at` alone leaves `recent=[] lexical=[] by_id=[] pending=[]`.
>
> What landed instead prevents the tombstone rather than repairing it. `upsert_message` raises
> `MessageIndexWriteError` on a failed write; `False` keeps its meaning of "this content is not
> indexable"; `handle_message_edit` tombstones only on `False`. No new column, no `restore`, no
> `ON CONFLICT` change.
>
> **`test_stale_upsert_does_not_resurrect_deleted_message` does not invert** — the Risks section
> below predicts it will, and that prediction applies to the `ON CONFLICT` fix, not to this one.
>
> Not taken: jittered retries inside `upsert_message`. `backfill_channel` resumes from a durable
> cursor and `on_message` absorbs, so with the tombstone gone a failed write is benign.
> See [`ANALYSIS_CORRECTIONS.md`](../ANALYSIS_CORRECTIONS.md) item 15. Guarded by `M-DAB065` and
> `M-DAB065B`.

- Type: BUG
- Severity / Payoff: **S1** (recalibrated; B4 filed S1, an independent verification pass held S2 —
  see Risks). Described by the reconciliation as "the worst data-loss defect in the corpus".
- Effort: M

## Context

Three independent decisions compose into unrecoverable data loss:

1. `upsert_message` swallows **every** exception and reports it as a benign `False`.
2. The edit handler reads `False` as "no longer eligible for indexing" and tombstones the message.
3. No code path can ever clear `deleted_at`. The `ON CONFLICT DO UPDATE` list updates 13 columns and
   omits it; only the fresh-INSERT branch writes `NULL`.

The tombstone is write-once and survives every subsequent re-index. Worse, it is
self-reinforcing: each later successful re-index still deletes the FTS row and refuses to re-insert
it, and forces `embedding_status='skipped'`. The row keeps its content faithfully updated while
being excluded from **both** the lexical and the semantic candidate sets.

`/rag backfill` does not heal it — backfill goes through the same `upsert_message`. The only repair
is the destructive `/rag delete` plus a re-backfill.

Trigger: `rag_enabled: true` (the default); any Discord `MESSAGE_UPDATE` for an indexed message

`delete_rag_data`, a big `/rag pregenerate`, a slow disk, or a permission blip. Also fires for any
other exception inside `upsert_message` (disk full, corruption).

Observable symptom: the message disappears from the bot's memory permanently and silently. The bot
answers "I don't have that in context" about a message plainly visible in the channel. Logs show one
`logger.error("Failed to index message ...")` line and nothing else; `mark_deleted` logs nothing on
success.

## Acceptance criteria

- [ ] `upsert_message` distinguishes "not indexable" from "write failed". `False` means a
      **business decision not to write** (empty text, out-of-scope bot message); a failed write
      **raises**.
- [ ] `handle_message_edit` only tombstones when the *content* became ineligible — never on an
      infrastructure error.
- [ ] `deleted_at = NULL` is added to the `ON CONFLICT DO UPDATE` list, or an explicit
      `mark_undeleted` / `restore` method exists. A re-index of a live Discord message is proof the
      message exists.
- [ ] The `hidden` carry-forward stops keying off the tombstone; `mark_deleted` stops overloading
      `hidden`, so the two flags stay independent.
- [ ] A message tombstoned by a transient error is retrievable again after a successful re-index —
      via `search_recent`, `search_lexical` **and** `get_messages_by_ids` — and reappears in
      `get_pending_embeddings`.
- [ ] Transient write failures are retried with jittered backoff before surfacing.

The atomic SQL form for the carry-forward, which also lands `B4-05`'s lost-update fix:

```sql
ON CONFLICT(message_id) DO UPDATE SET
    ...,
    hidden = CASE WHEN ?hidden_override IS NULL
                  THEN message_index.hidden ELSE excluded.hidden END,
    deleted_at = NULL
```

The write-semantics design (`I2-13`) adds two exception types to `sqlite_utils.py`:

```python
class TransientDBError(Exception):
    """Lock contention or a busy database. Retrying is expected to work."""

class PermanentDBError(Exception):
    """Constraint violation, schema mismatch, corruption. Retrying will not help."""

_TRANSIENT = ("database is locked", "database table is locked", "database schema has changed")

def classify(exc: sqlite3.Error) -> Exception:
    if isinstance(exc, sqlite3.OperationalError) and any(m in str(exc) for m in _TRANSIENT):
        return TransientDBError(str(exc))
    return PermanentDBError(str(exc))
```

with jittered retry inside the write lane and a bounded in-memory `PendingWriteQueue` so
`rag_event_coordinator` **defers** instead of tombstoning. There are 13 sites in the codebase with
the same silent-`False` shape; each needs a deliberate catch-or-propagate decision.

## Test to add

`tests/test_bug_regressions.py`, class `TombstoneRecoveryTest`:

```
happy path:
    index -> mark_deleted -> upsert_message with the same id
    assert deleted_at IS NULL
    assert search_recent, search_lexical and get_messages_by_ids all return the message again
    assert get_pending_embeddings includes it

error path:
    patch MessageIndexService.upsert_message to raise sqlite3.OperationalError("database is locked")
    drive RagEventCoordinator.handle_message_edit
    assert mark_deleted_async was NOT called
    assert the row is still retrievable
```

If the defect returns, the error-path test fails because `mark_deleted_async` was awaited.

## Risks and notes

- **One existing test pins the current behaviour and WILL FAIL.**
  `tests/test_message_rag_services.py:158`
  `MessageIndexServiceTest.test_stale_upsert_does_not_resurrect_deleted_message` does
  `_upsert(353, ...)` -> `mark_deleted(353)` -> `_upsert(353, "Late edit event")` ->
  `assertNotIn(353, recent_ids)`. Adding `deleted_at = NULL` to the `ON CONFLICT` list **inverts**
  this assertion. The ticket must decide whether a *stale* edit event should resurrect a message and
  rewrite the test rather than delete it. That test is a deliberate statement of intent by whoever
  wrote it; treat it as a design question, not an obstacle.
- `tests/test_discord_orchestration.py:143`
  `RagEventCoordinatorTest.test_ineligible_edit_marks_existing_index_row_deleted` uses
  `index_discord_message_async=AsyncMock(return_value=False)` and asserts
  `mark_deleted_async.assert_awaited_once_with(10)`. Still valid for genuine ineligibility, but it
  is exactly the contract that must be split into "ineligible" vs "write failed".
- Must keep passing: `tests/test_message_rag_services.py:132`, `:102`, `:119`;
  `tests/test_discord_orchestration.py:128`; `tests/test_bug_regressions.py:90`.
- **Severity is contested.** The independent pass held **S2**, reasoning that what is lost is
  derived index state, not user content — the message is intact in Discord and in
  `message_index.content_text`, and there *is* a (destructive) repair path. It called it "the
  closest of the ten to S1" and stressed that the trigger is ordinary, not exotic.
- **Land `DAB-095` first.** WAL plus an explicit busy timeout shrinks the lock-hold window that
  produces this. But note the measurement: WAL alone does **not** fix it — with a write lock held, a
  concurrent *write* still fails after 5.01 s in both journal modes. The semantics change is
  required regardless.
- `I2-13` provides a rollback flag: `db.raise_on_write_failure: false` restores `False`-returning
  behaviour while keeping the retries. Ship the retries first if the 13-site audit slips.
