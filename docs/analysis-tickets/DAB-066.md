## Context

The one-time migration of the shared `token_usage.db` RAG tables into `message_rag.db` copies only
the **intersection** of target and legacy columns, using `INSERT OR IGNORE`.

`INSERT OR IGNORE` extends conflict resolution to `NOT NULL` violations. So when the legacy schema
lacks a column the target declares `NOT NULL` with no default, **every row is silently skipped** —
and the migration then unconditionally writes the ledger row and logs success.

The ledger gates every later boot, so it is never retried. `delete_rag_data()` does not clear the
ledger either.

The seeded lead predicted an abort. It does not abort. The truth is worse.

An independent verification pass reproduced the scenario verbatim and added the counts per missing

```

B. legacy MISSING content_hash (NOT NULL, no default)        -> migrated rows:    0 | ledger written

```

Observable symptom: after the upgrade the bot has no memory at all of anything said before the
upgrade. `/rag status` reports `messages: 0`. The log says the copy succeeded.

## Acceptance criteria

- [ ] `OR IGNORE` is gone for anything except genuine primary-key collisions. Use
      `INSERT INTO ... ON CONFLICT(message_id) DO NOTHING` so `NOT NULL` violations raise.
- [ ] Required target columns the legacy schema lacks are either supplied (a recomputed
      `content_hash`, a `COALESCE`d `indexed_at`) or the migration refuses to run.
- [ ] Rows are counted **before and after**, compared, and the ledger row is **not written** on a
      mismatch. Log the delta at WARNING/ERROR.
- [ ] The ledger name includes a schema fingerprint so a fixed migration can re-run.
- [ ] A drifted-schema legacy database either migrates completely or fails loudly and retryably.
      `0 rows + ledger written` must become impossible.

## Files to touch

- `src/services/message_index_service.py` — `_migrate_legacy_database` (`:602-697`), specifically
  the column intersection (`:641-658`), the ledger insert (`:685-687`), the success log (`:689`).
- `src/services/pin_service.py` — the sibling pin migration has the *opposite* bug (`B4-04`,
  `DAB-068`: an explicit column list produces `no such column`, which is swallowed and retried
  forever, at `pin_service.py:77-95` and `:97-98`). Fixing one without the other leaves the pair
  inconsistent.

The `I2-03` design replaces the intersection with a declared map plus a count assertion:

```python
LEGACY_V1_COLUMNS = {
    "message_index": [
        ("message_id", "message_id"), ("guild_id", "guild_id"),
        ("channel_id", "channel_id"), ("author_id", "author_id"),
        ("author_name", "author_name"), ("is_bot", "is_bot"),
        ("reply_to_message_id", "reply_to_message_id"),
        ("created_at", "created_at"), ("indexed_at", "indexed_at"),
        ("content_text", "content_text"),
        ("attachment_summary", "attachment_summary"),
        ("content_hash", "content_hash"), ("hidden", "hidden"),
        ("deleted_at", "deleted_at"),
        # embedding_eligibility_text has no legacy source -> filled from content_text
    ],
    ...
}

for table, mapping in LEGACY_V1_COLUMNS.items():
    missing = [src for _dst, src in mapping if not legacy_column(conn, table, src)]
    if missing:
        raise MigrationError(f"legacy {table} is missing {missing}; refusing a partial copy")

    expected = conn.execute(f'SELECT COUNT(*) FROM legacy."{table}"').fetchone()[0]
    before   = conn.execute(f'SELECT COUNT(*) FROM main."{table}"').fetchone()[0]
    conn.execute(f'INSERT INTO main."{table}" ({dst_sql}) SELECT {src_sql} FROM legacy."{table}"')
    copied = conn.execute(f'SELECT COUNT(*) FROM main."{table}"').fetchone()[0] - before

    if copied != expected:
        raise MigrationError(
            f"legacy {table}: expected {expected} rows, copied {copied}. "
            "Transaction rolled back; the legacy file is untouched.")
```

Three changes carry the weight: a declared map (an added target column can no longer shrink the
intersection), plain `INSERT` (a duplicate PK now raises), and a copied-vs-expected assertion inside
the transaction (a short copy rolls back and never writes the ledger row).

The simplest correct alternative: `SELECT` the legacy rows into Python and route them through
`upsert_message`, which computes `content_hash`/`indexed_at` itself.

## Test to add

`tests/test_rag_optimization.py` (beside the existing happy-path test) or
`tests/test_bug_regressions.py`, class `LegacyMigrationTest`:

```
happy path:
    legacy DB with the current schema -> all rows appear, ledger written

error path:
    legacy message_index WITHOUT content_hash / indexed_at
    assert EITHER the rows are migrated with a recomputed hash
        OR the migration raises/logs and the ledger row is ABSENT (so it retries)
    assert COUNT(*) > 0
```

The current behaviour — `0 rows + ledger written` — must fail this test.

## Risks and notes

- **The precondition is not reachable from this repository's history, and that is why severity is
  contested.** An independent pass diffed the `message_index` CREATE body across every commit that
  ever touched the file (`d923856, 88e330b, 5e45599, 5daa9ea, cbf32b6, f22c29a, 784e71e`) and found
  the NOT-NULL column set byte-identical in all seven revisions. The one and only column ever added
  is `embedding_eligibility_text TEXT` — nullable, introduced in `784e71e`, the very commit that
  added this migration. Value-producing sites confirm `author_name` (`:341`), `content_hash`
  (`:419`) and `indexed_at` (`:427`) can never be NULL. Its verdict: **S3-Minor (latent S1 for the
  next schema change)**. It also noted it can only speak to what *this* history could have written;
  an out-of-tree fork or a hand-edited schema could have produced the precondition.
- The master register held **S1** because the failure mode is total, permanent and silent, and
  because it "converts to a genuine S1 the moment anyone adds a NOT NULL column without a default
  to `message_index` — which is exactly the kind of change `AGENTS.md` says to make via
  `_ensure_column`". This is insurance against a change the project is documented to make.
- **The existing test cannot catch this and will keep passing.**
  `tests/test_rag_optimization.py:223`
  `RagDatabaseIsolationTest.test_legacy_rag_data_is_copied_to_dedicated_database_only` builds its
  legacy database with `MessageIndexService(token_db, ...)`, i.e. the *current* schema — which is
  exactly why the bug ships. Add a drifted-schema sibling; do not modify the existing one.
- Cross-link with `I2-01` (a `PRAGMA user_version` migration runner) before implementing. That
  proposal subsumes this migration into an ordered, atomic, adoption-aware runner and is the right
  long-term shape. `I2-03`'s fix is explicitly independent of it and can ship first.
