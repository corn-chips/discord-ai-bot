# DAB-073: Pins have absolute priority and can starve retrieval to zero slots

**Status: LANDED** in `36bf261` — a retrieval floor is reserved before pins are allocated, so pins can no longer starve retrieval to zero slots.

- Type: BUG
- Severity / Payoff: S2
- Effort: S
- Priority score: 6.0 — impact High (3) x frequency Occasional (2) / effort S (1)
- Confidence: **VERIFIED** — slot table and end-to-end waste both measured
- Merged IDs: `B4-09`, `C4-09`, `C4-10`, `C4-11`
- Blocks / Blocked by: **blocks `DAB-150`.** Agree the retrieval floor here before capping pins at
  ingest; both edit `context_pack_builder.py` and `pin_service.py`.

## Context

`build_context_pack` allocates slots to pins **first and unconditionally**, up to the whole budget.
With `rag_max_context_messages_low: 4`, four pins consume the entire pack and
`available_retrieval_slots` returns 0.

Nothing short-circuits. `retrieve()` has already run `search_recent`, `search_lexical` **and** a live
`embed_texts` round trip before slots are computed, then materialises 12 `MessageContext` objects
that `build_context_pack` discards.

Three amplifiers ride on the same code path:

- a pin has **no length cap anywhere**, so one 100 KB pin rides in every prompt forever;
- pins are ordered `pinned_at ASC`, so the *oldest* junk pins claim the slots permanently and newer
  legitimate pins are shut out too;
- `get_pins` has **no `LIMIT`**, so every pin in the channel is loaded and materialised on every
  message and then thrown away.

The allocator:

```python
    @staticmethod
    def _priority_slot_counts(pin_count: int, anchor_count: int, max_messages: int) -> tuple[int, int]:
        """Reserve room for a reply anchor without discarding pinned memory."""
        max_messages = max(1, int(max_messages or 1))
        reserve_anchor = 1 if pin_count and anchor_count and max_messages > 1 else 0
        pin_slots = min(pin_count, max_messages - reserve_anchor)
        anchor_slots = min(anchor_count, max_messages - pin_slots)
        return pin_slots, anchor_slots
```

## Acceptance criteria

- [ ] A hard floor is reserved for retrieved context. Either
      `pin_slots = min(pin_count, max(1, max_messages - reserve_anchor - MIN_RETRIEVAL_SLOTS))` with
      `MIN_RETRIEVAL_SLOTS` configurable (default 2), or the fraction form
      `pin_slots = min(pin_count, max(1, max_messages // 2))`.
- [ ] With 20 pins and `max_messages=8`, at least one non-pin item survives in the pack.
- [ ] Pins are ordered `pinned_at DESC` so newer pins win the contested slots, **and** `get_pins`
      takes a `LIMIT` derived from `max_messages`. These two must land together — a `LIMIT` on an
      ASC sort silently keeps only the oldest pins.
- [ ] `retrieve()` short-circuits when `available_slots <= 0` **before** the embedding call, reusing
      the existing `pins_only` fast path at `hybrid_context_retriever.py:514-529`
      (`retrieval_mode="pins_only"` at `:527`).
- [ ] The `no_available_slots` reason recorded at `:588` is surfaced somewhere an operator sees it.
- [ ] `/pin` warns the user when the channel's pin count is about to starve retrieval.

## Files to touch

- `src/services/context_pack_builder.py` — `_priority_slot_counts` (`:101-108`),
  `build_context_pack` slot maths (`:93-99`), `available_retrieval_slots` (`:110-123`),
  `build_pinned_context` (`:33-45`).
- `src/services/pin_service.py` — `get_pins` `LIMIT` + `DESC` (`:140-162`, ordering at `:154`).
- `src/services/hybrid_context_retriever.py` — `_load_pins` (`:443-447`, call at `:512`), the early
  exit before `_embed_query` (`:553`), `rerank_pool` sizing (`:576`).
- `config.yaml` + the four-place rule for `MIN_RETRIEVAL_SLOTS`.

A structurally better alternative worth considering: **stop charging pins against the same budget
at all.** Pins are channel configuration, not retrieved context; give them their own
character-bounded region of the prompt. `PinService.get_pins_for_prompt` (`:185-204`) already exists
for exactly that, though it is currently dead code — see `DAB-150` for the conflicting
delete-vs-keep recommendation.

Also worth an index while you are here:
`CREATE INDEX IF NOT EXISTS idx_pinned_channel_at ON pinned_messages (channel_id, pinned_at);`
— `pinned_messages` has `(channel_id)` but `get_pins` does `ORDER BY pinned_at ASC`, which is a temp
sort per call.
