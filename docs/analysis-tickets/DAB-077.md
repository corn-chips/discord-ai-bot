# DAB-077: `_reconcile_embedding_eligibility` full-table-scans on every construction, costing 97.8% of `DiscordBot.__init__`

**Status: OPEN** — `_reconcile_embedding_eligibility` is still called unconditionally from `_ensure_schema` (`message_index_service.py:322`). Its blocker DAB-083 landed in Phase 4; this did not. Quote the absolute saving at your corpus size, not the 57,000x ratio (`ANALYSIS_CORRECTIONS.md`, "Restated figures").

- Type: IMPROVEMENT
- Severity / Payoff: S2. **1938 ms -> 0.034 ms per boot at 100k messages (57,134x)**; boot time
  drops from ~2.67 s to ~0.06 s (~45x)
- Effort: S — one guard and one ledger insert
- Priority score: 8.0 — impact Medium (2) x frequency Continuous (4) / effort S (1)
- Confidence: **VERIFIED** — measured independently by three lanes with agreeing numbers
- Merged IDs: `B4-18`, `C5-02`; prototyped as `I3-05`, independently as `I2-14`
- Blocks / Blocked by: **blocked by `DAB-083`** (the ledger table must be owned by `_ensure_schema`
  first, or the new `SELECT` raises fatally from `__init__`). **Blocks `DAB-087`** (widening the
  eligibility regex must bump the fingerprint).

## Context

`_ensure_schema` ends by unconditionally calling `_reconcile_embedding_eligibility`, which
`SELECT`s **every** row of `message_index` joined to `message_embeddings`, `.fetchall()`s the lot
into memory, re-evaluates `_embedding_is_trivial` in Python per row (two `re.findall` calls plus a
DOTALL `re.sub` on the fallback path), and issues per-row `UPDATE`s — all inside the single write
transaction `_ensure_schema` holds.

It is O(index size) and runs on **every** construction, not only when the triviality thresholds
changed. `DiscordBot.__init__` is synchronous and `main.py:45` calls it from inside
`async def main()`, so this is event-loop-blocking time before the gateway connects.

Reconciliation is a pure function of
`(eligibility_text, attachment_summary, embedding_min_words, embedding_min_alphanumeric_chars,
embedding_model)`, and every insert path already applies the same rule. So if the *rules* have not
changed since the last successful reconcile, the scan is provably a no-op.

## Evidence

- Call site 1: `src/services/message_index_service.py:265`, the last statement in the
  `_ensure_schema` transaction.
- Call site 2: `:672`, inside `_migrate_legacy_database` — **this one must bypass the gate**, it
  reconciles freshly imported rows.
- The scan itself: `:705-722`. The query is one physical line at `:706`:

```sql
SELECT m.message_id, m.content_text, m.embedding_eligibility_text,
       m.attachment_summary, e.embedding_status
FROM message_index m JOIN message_embeddings e ON e.message_id = m.message_id
WHERE e.embedding_model = ?
```

No predicate narrows it. `_embedding_is_trivial` is at `:698-703`.

The 1.94 s vs 2.61 s discrepancy between lanes is explained: the larger figure includes the
surrounding DDL and the 11 `PRAGMA table_info` calls in `_ensure_column`; the smaller isolates the
reconcile. A third lane independently measured 230 ms at 100k rows in its own environment.

A compounding hazard on the same code: changing `rag_embedding_model` **or**
`rag_embedding_dimensions` (both feed the composite key at `:89`) rewrites every embedding row to
`'pending'` at `:196-209`, so the next boot both scans everything and queues the entire history for
re-embedding — an unbounded API bill from a one-line config edit, with no confirmation.

## Acceptance criteria

- [ ] The reconcile is gated on a named row in `rag_migrations` whose name encodes every input to
      the triviality rule.
- [ ] A second construction over the same seeded database executes **zero** `UPDATE
      message_embeddings` statements.
- [ ] Changing `embedding_min_words`, `embedding_min_alphanumeric_chars` or `embedding_model`
      produces a new ledger key, so the scan re-runs exactly when it must.
- [ ] The `_migrate_legacy_database` call site at `:672` **bypasses** the gate.
- [ ] Boot time at 100k messages drops from ~2.6 s to well under 100 ms.
- [ ] A `RECONCILE_RULES_VERSION` constant (or a hash of the rule's constants) is part of the
      fingerprint, so a future change to `_embedding_is_trivial` cannot silently leave stale rows.

If the gate is removed, the first test's UPDATE count goes non-zero. If the fingerprint is
incomplete, the second test fails.

## Risks and notes

- **Hard prerequisite: `DAB-083`.** `rag_migrations` is not created by `_ensure_schema` today; only
  the two migration paths create it defensively. A ledger `SELECT` added to `_ensure_schema` against
  a fresh Case-A database raises `OperationalError: no such table: rag_migrations` **from inside
  `__init__`, which is fatal**. Ship `DAB-083` in the same change or before it.
- **The fingerprint must include everything the trivia rule reads.** If someone later adds a term to
  `_embedding_is_trivial` without bumping the fingerprint, stale rows persist silently. The
  `RECONCILE_RULES_VERSION` constant is not optional.
- **Interlock with `DAB-087`.** The non-Latin fix changes `_embedding_is_trivial`'s regexes. The
  fingerprint as written does **not** change when the regex changes, so without a version bump every
  existing non-Latin row stays `skipped` forever. That is why `DAB-077` blocks `DAB-087`.
- Existing tests that must keep passing:
  - `tests/test_rag_optimization.py:45`
    `test_trivial_messages_stay_fts_searchable_and_edits_transition_both_ways` — these transitions
    happen at insert time (`:425`), not in the reconcile, so a ledger gate does not affect them.
    State that explicitly in the commit message.
  - `tests/test_rag_optimization.py:54`
    `test_real_discord_metadata_does_not_make_trivial_text_eligible`.
  - `tests/test_message_rag_services.py:246`
    `test_embedding_model_change_requeues_existing_message` — the fingerprint includes
    `self.embedding_model`, so a model change must still force a re-run. This test is the guard.
  - `tests/test_rag_optimization.py:223`
    `test_legacy_rag_data_is_copied_to_dedicated_database_only` — drives the `:672` call site that
    must bypass the ledger.
- The two lanes agree on the fix shape; `I2-01`'s migration-runner proposal explicitly keeps this
  **out** of the version runner ("gated on a fingerprint row, not a version"), so the two designs do
  not conflict.
