## Context

The only scope index on `message_index` is `(guild_id, channel_id, created_at DESC)`. The default
retrieval path is channel-scoped (`config.yaml:41`, `cross_channel_enabled: false`), so
`_scope_clause` emits `m.channel_id = ?` with `guild_id` never bound.

SQLite skip-scans the leading column, visiting every distinct `guild_id`, and then builds a temp
B-tree to satisfy `ORDER BY created_at DESC` — for a query that wants 12-15 rows. Latency is exactly
linear in corpus size.

  `LIMIT ?` at `:1096`.
- Scope clause: `:1047-1061`, the channel branch returning `"m.channel_id = ?"` at `:1061`.
- The only index available: `:151-155`
  (`idx_message_index_scope_time ON message_index (guild_id, channel_id, created_at DESC)`),
  plus `idx_message_index_reply` at `:156-161`.

> One lane cites `_scope_clause` at `:298-311`. That is wrong; the working tree has it at
> `:1047-1061`. Use 1047-1061.

`EXPLAIN QUERY PLAN`, 100k rows, channel scope — before:

```
SCAN m USING INDEX idx_message_index_scope_time
USE TEMP B-TREE FOR ORDER BY
```

after adding `(channel_id, created_at DESC)`:

```
SEARCH m USING INDEX idx_channel_time (channel_id=?)
```

Independent prototype (100,000-row seeded DB, production schema copied verbatim) — before:

```
search_recent (single channel): 1.542 ms
  SEARCH m USING INDEX idx_message_index_scope_time (ANY(guild_id) AND channel_id=?)
  USE TEMP B-TREE FOR ORDER BY

search_recent (cross-channel guild): 100.773 ms
  SEARCH m USING INDEX idx_message_index_scope_time (guild_id=?)
  USE TEMP B-TREE FOR ORDER BY
```

after:

```
search_recent (single channel): 0.055 ms      (29.0x)
  SEARCH m USING INDEX idx_cp (channel_id=?)        <- no temp B-tree

search_recent (cross-channel guild): 0.056 ms  (1870x)
  SEARCH m USING INDEX idx_gp (guild_id=?)          <- no temp B-tree
```

The temp B-tree disappears: with `created_at DESC` as the second index column, SQLite walks the
index in order and stops after 12 rows.

Third lane, realistic density (10 channels x 10,000 rows):

```
baseline (shipped indexes)             30.811 ms
plain  (channel_id, created_at DESC)    0.034 ms ->  914x
PARTIAL (recommended)                   0.026 ms -> 1200x
```

and guild scope with `cross_channel_enabled: true`: 79.042 ms -> 0.101 ms = **783x**.

Latency curve confirming linearity: 0.646 ms @1k -> 3.063 ms @10k -> 29.26 ms @100k -> 87.17 ms
@300k. Index build cost: 116 ms, +4.7 MB on a 535 MB database.

Bonus, the same index helps a second query — `get_pending_embeddings` channel-filtered goes
3.523 ms -> 1.972 ms (1.8x) with the temp B-tree gone.

## Risks and notes

- **Plain vs partial is an unresolved disagreement between two lanes. Settle it in review.**
  - The partial version matches the `WHERE hidden = 0 AND deleted_at IS NULL` predicate on every
    read path and shrinks the index; at 100k rows the five-index set costs 12.4 MB total, ~3% of
    the file.
  - The plain version "serves any future query that omits the `hidden`/`deleted_at` predicate,
    whereas a partial index is silently skipped if the `WHERE` clause does not match
    syntactically". Its lane recommends plain.
  - Both read identically and cost the same to write. **Do not add all four** — that is +40% write
    cost for zero read benefit.

  Index-set comparison:

  | index set | DB size | write cost | recent(channel) | recent(guild) |
  |---|---|---|---|---|
  | shipped only (2) | 88.8 MiB | **52.3 us/row** | 1.595 ms | 104.742 ms |
  | +2 plain | 94.0 MiB | 76.7 us/row | **0.055 ms** | **0.055 ms** |
  | +2 partial | 93.8 MiB | 76.5 us/row | 0.055 ms | 0.056 ms |
  | +4 (both) | 100.8 MiB | **105.1 us/row** | 0.057 ms | 0.058 ms |

- **The one deliberate regression in the whole backlog: writes go 52.3 -> 76.7 us/row (+46%)**, and
  the database grows ~5 MiB per 100k messages. At the post-fix backfill rate that turns 51,320 msg/s
  into roughly 35,000 msg/s — still 50x the shipped rate. Accept it knowingly.
- **Sequencing against backfill batching (`DAB-076` / `I3-06`):** the +46% write cost lands on the
  backfill first. One lane notes the batching change "benefits from `I3-04` being in place (the
  extra index write cost is amortised inside the batch)"; the other direction says sequence the DDL
  after the batching if the first-boot backlog is the binding concern. Either order works; be
  deliberate.
- Rollback is `DROP INDEX` — instant, no data touched.
- Existing tests that exercise `search_recent` (all plan-change only, none should break):
  `tests/test_sqlite_services.py:88` (calls at `:113`);
  `tests/test_message_rag_services.py` at `:83`, `:110`, `:139`, `:166`, `:233`;
  `tests/test_rag_optimization.py:146,163,169` (mocked). These matter for the **partial** index in
  particular: the predicate is only used when the query's `WHERE` matches syntactically, and
  `search_recent` does carry `AND m.hidden = 0 AND m.deleted_at IS NULL` at `:1092-1093` — but a
  plan assertion is the only way to prove it.
- One lane's numbers were taken at 100k-350k indexed messages. A hobbyist single-guild install is
  two to three orders of magnitude smaller, where 30 ms is unremarkable. This is Tier 0 because it
  costs two lines and there is no reason to leave a 1200x on the table, not because 30 ms is
  currently hurting anyone.
