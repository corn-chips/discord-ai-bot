# DAB-083: `rag_migrations` is not owned by `_ensure_schema`; its existence is an accident of construction order

- Type: BUG
- Severity / Payoff: S3
- Effort: XS — move one `CREATE TABLE IF NOT EXISTS`
- Priority score: 4.0 — impact Medium (2) x frequency Rare (1) / effort XS (0.5)
- Confidence: **VERIFIED** — reproduced as a two-case experiment during reconciliation
- Merged IDs: `B4-15`, `C3-12`
- Blocks / Blocked by: **blocks `DAB-077`.** A ledger read added to `_ensure_schema` without this
  raises from inside `DiscordBot.__init__`, which is fatal (`DAB-067`).

## Context

`rag_migrations` is the named-row ledger that gates the two one-shot migrations. It is **not**
created by `_ensure_schema`. It is created defensively inside the two migration paths that use it —
`_migrate_legacy_database` in `MessageIndexService` and the pin migration in `PinService`.

Whether the table exists on a fresh install is therefore an accident of which service constructs
first. Both possible answers were reproduced:

- Case A, `MessageIndexService` alone on a fresh path: `rag_migrations` **absent**.
- Case B, `TokenTracker` constructed first (as in `DiscordBot.__init__`): **present**.

Two reports appeared to contradict each other on this; both were right, under different scopes.

This is minor on its own. It matters because `DAB-077` — the highest-payoff-per-line fix in the
corpus — wants to add a ledger read to `_ensure_schema`, and on a Case-A database that read raises
`OperationalError: no such table: rag_migrations` from a synchronous constructor.

## Evidence

- The ledger's `CREATE TABLE IF NOT EXISTS` lives at `src/services/message_index_service.py:620-627`
  — i.e. **inside** `_migrate_legacy_database` (`def` at `:602`), not in `_ensure_schema`
  (`def` at `:126`).
- The read that gates the migration: `:629`. The insert: `:686`.
- The second, independent creation site: `src/services/pin_service.py:63-70`.
- `_ensure_schema`'s own DDL runs `:126-265` and never mentions `rag_migrations`.

Probe `p01_migrations_ledger.py`:

```
rag_migrations present: False        (Case A: MessageIndexService alone, fresh path)

CASE C: a naive ledger check against a fresh (case A) db
  -> SELECT on rag_migrations RAISES: OperationalError no such table: rag_migrations
```

The reconciliation's two-case experiment:

| Case | Setup | `rag_migrations` |
|---|---|---|
| A | `MessageIndexService(fresh_path)` alone | **absent** |
| B | `TokenTracker` first, then the index service (as in `__init__`) | **present** |

A second consequence noted by the same finding: the ledger name is path-independent, so a fresh
install *burns* both one-shot migrations while logging "Copied legacy data" that copied nothing.

Why the raise is fatal rather than degrading: `MessageIndexService.__init__` is called
synchronously from `DiscordBot.__init__` (`discord_bot.py:355-363`), and an unreadable legacy
database aborting `__init__` is already filed as `DAB-067` — a permanent boot loop.

## Reproduction

```python
import tempfile, os, sqlite3
from src.services.message_index_service import MessageIndexService
d = tempfile.mkdtemp()
svc = MessageIndexService(os.path.join(d, "message_rag.db"))     # no legacy_db_path
con = sqlite3.connect(os.path.join(d, "message_rag.db"))
print(con.execute(
    "SELECT name FROM sqlite_master WHERE type='table' AND name='rag_migrations'").fetchall())
# []  -> absent
con.execute("SELECT 1 FROM rag_migrations WHERE name = ?", ("x",))
# sqlite3.OperationalError: no such table: rag_migrations
```

## Acceptance criteria

- [ ] `CREATE TABLE IF NOT EXISTS rag_migrations(...)` is executed by `_ensure_schema`, so every
      construction of `MessageIndexService` produces a database containing it.
- [ ] The two defensive creation sites (`message_index_service.py:620-627`,
      `pin_service.py:63-70`) still work — they are `IF NOT EXISTS`, so they become no-ops — or are
      removed once the schema owns the table.
- [ ] `SELECT 1 FROM rag_migrations` succeeds on a database created by `MessageIndexService(path)`
      with **no** `legacy_db_path`.
- [ ] A fresh install no longer records a completed migration for work it did not do (or, if it
      must, the row says so explicitly).

## Files to touch

- `src/services/message_index_service.py` — move the `CREATE TABLE IF NOT EXISTS rag_migrations`
  from `:620-627` into `_ensure_schema` (`:126-265`), before the `_reconcile_embedding_eligibility`
  call at `:265`.
- `src/services/pin_service.py:63-70` — leave the `IF NOT EXISTS` (harmless) or remove it once the
  schema owns the table. If `PinService` can be constructed against a database no
  `MessageIndexService` has touched, **leave it**.

## Test to add

`tests/test_sqlite_services.py`, extending the existing service-behaviour class:

test_rag_migrations_ledger_exists_on_a_fresh_index:

## Risks and notes

- **No existing test breaks.** No test asserts the absence of this table.
- Existing databases already have the table if either migration ever ran; `IF NOT EXISTS` makes the
  move idempotent for everyone else.
- Do this **before** `DAB-077`. The reconciliation is explicit: "a ledger check added to
  `_ensure_schema` without first moving `CREATE TABLE IF NOT EXISTS rag_migrations` into
  `_ensure_schema` raises from inside `__init__`, which is fatal."
- The broader answer is `I2-01`'s `PRAGMA user_version` migration runner, which replaces this
  named-row ledger entirely (it keeps the table readable for the two existing legacy rows but writes
  no new ones, and deletes it at v4 once no deployment can still be pre-v1). That is an M-effort
  change with a 20/20-assertion prototype; this ticket is the XS stopgap that unblocks `DAB-077`
  today.
- Note the separate related finding `DAB-084`: `embedding_vector` is an untagged BLOB|TEXT union in
  a column declared TEXT. Same file, same "schema is implicit" theme, not a dependency.
