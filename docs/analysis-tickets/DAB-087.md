# DAB-087: Hybrid RAG is blind to every non-Latin script

**Status: PARTIAL** — the lexical half landed in `4558643`: `_build_fts_query` tokenises on `[\w@#./:-]{2,}`, so CJK, Cyrillic, Arabic and Greek queries now reach the index. **The semantic half is deferred, and this ticket's stated blocker is refuted** — the reconcile fingerprint does exist (`_eligibility_fingerprint`, landed `f96717a`, one commit earlier). The named prerequisite for taking the semantic half is backfill pacing plus a recoverable `failed` state, and it is recorded in `_embedding_is_trivial`'s docstring. **Do not edit that function, including its docstring**: `_eligibility_fingerprint` hashes its source text, so a reformat alone starts a 16-40 minute paid re-embedding run. Zero-width stripping (`C4-07`) never landed — a 900-char zero-width query still collapses to `"ea"` — and NFKC was measured and deliberately refused (`M-DAB087B`).

- Type: BUG
- Severity / Payoff: S2 with an XS-to-S fix — widen two regexes. Described by the reconciliation as
  belonging "at #21 for any non-English guild".
- Effort: S (the regex change is XS; the FTS rebuild and fingerprint bump make it S)
- Priority score: 3.0 — impact High (3) x frequency Rare (1, under an assumed-English deployment) /
  effort S (1)
- Confidence: **VERIFIED** — measured across seven scripts
- Merged IDs: `C4-01`, `C4-07`
- Blocks / Blocked by: **blocked by `DAB-077`** — this changes the eligibility rule, so the
  reconcile fingerprint must be bumped in the same change or existing non-Latin history stays
  `skipped` forever. Also needs an FTS rebuild path that does not exist (`DAB-071`).

## Context

Two independent regexes hard-code the Latin alphabet, and they sit on the *two* non-recency
retrieval legs.

For non-Latin text the token list is empty, so `_build_fts_query` returns `None` and
`search_lexical` bails before touching SQLite. Simultaneously `words == []` and `chars == 0`, so
`_embedding_is_trivial` returns `True`, `embedding_status` is set to `"skipped"`, and the message is
never embedded — so it can never be a semantic candidate either.

In a non-English server hybrid retrieval degrades to `search_recent` only — "last N messages" —
silently, with no log line and no `fallback_reason`.

`C4-07` is the same regex hurting Latin text: the token pattern requires **two or more consecutive**
matching characters, so a zero-width character between every letter destroys the query.

    def _embedding_is_trivial(self, content_text: str, attachment_summary: str = "") -> bool:

For a 1,800-character query the entire FTS expression collapses to a single two-letter phrase.

**Crucial asymmetry:** the *index* side is fine. FTS5's `unicode61` tokenizer treats ZWSP as a
separator, so a stored `secret\u200bproject\u200bphoenix` **is** found by the plain query
`secret project phoenix` (probe returned `[5006]`). Only the query-construction path is broken.

A dead defence worth a comment: `cleaned = token.replace('"', '""')` at `:1119` can never do
anything — the regex one line above cannot produce a token containing `"`. It reads as if it is the
load-bearing defence when the real defence is the character class.

## Acceptance criteria

- [ ] `_build_fts_query` produces a non-`None` query for CJK, Cyrillic, Arabic, Hebrew, Greek and
      Thai input, using a Unicode-aware class such as `re.findall(r"\w{2,}", q, flags=re.UNICODE)`
      minus the FTS5 metacharacters, which must still be excluded.
- [ ] `_embedding_is_trivial` counts non-Latin characters, using `[^\W_]` rather than `[A-Za-z0-9]`.
- [ ] Zero-width characters are stripped (`unicodedata.category(ch) == 'Cf'`) and NFKC applied
      **before** tokenisation. `_build_fts_query("bud\u200bget meet\u200bing")` yields `"budget"`
      and `"meeting"` phrases.
- [ ] `RECONCILE_RULES_VERSION` (from `DAB-077`) is bumped, so already-indexed non-Latin rows are
      re-evaluated and flip from `skipped` to `pending`.
- [ ] The Latin boundary cases are unchanged: `"hi"` (2 chars / 1 word) and `"ok"` still classify as
      trivial.
- [ ] If the FTS5 tokenizer changes, a `rebuild_fts_index()` path exists and is invoked — otherwise
      the change is a no-op for every existing row.

## Risks and notes

- **Two hard interlocks. Neither is optional.**
  1. **The tokenizer change requires an FTS rebuild that does not exist.** `tokenize` is hard-coded
     at `:258`, and the only `DELETE FROM message_search_fts; INSERT ... SELECT` rebuild lives
     inside `_migrate_legacy_database` (`:673-684`), gated by the `rag_migrations` ledger, so it
     runs at most once. `DAB-071`: "there is no way to reindex". Ship `rebuild_fts_index()` with the
     tokenizer change or the change is a no-op for all existing rows. **For CJK specifically,
     widening the query regex is not enough** — scriptio-continua languages still will not match at
     the index level without a trigram or ICU tokenizer.
  2. **Widening `_embedding_is_trivial` changes the reconcile rule.** Every existing non-Latin row
     is currently `embedding_status = 'skipped'`; only `_reconcile_embedding_eligibility` can flip
     them back. If `DAB-077`'s ledger gate lands first, the fingerprint
     `reconcile_eligibility:{model}:{min_words}:{min_alphanumeric_chars}` does **not** change when
     the regex changes — so the backlog would never be re-evaluated. Bump
     `RECONCILE_RULES_VERSION` in the same change.
- **Existing tests that pin the Latin behaviour and must keep passing:**
  - `tests/test_rag_optimization.py:45`
    `test_trivial_messages_stay_fts_searchable_and_edits_transition_both_ways` — `"hi"` must stay
    `skipped`, `"this message is eligible"` must be `pending`, `"ok"` must stay `skipped`. These are
    the boundary cases for the widened class.
  - `tests/test_rag_optimization.py:54`
    `test_real_discord_metadata_does_not_make_trivial_text_eligible`.
  - `tests/test_message_rag_services.py:39` `test_lexical_search_finds_exact_terms` — the only
    end-to-end FTS assertion in the suite.
  - `tests/test_rag_optimization.py:223` also asserts a lexical hit (`"searchable"` -> `[31]`), so it
    will catch a tokenizer regression.
- **`search_lexical`'s OR-expansion is itself a measured cost centre** — capping the number of OR'd
  FTS terms is 186.6 -> 4.9 ms (38x) at 350k, at medium risk because recall changes. A
  Unicode-widened token class will match strictly *more* tokens. Land both `_build_fts_query`
  changes together, or measure before and after.
- This is Tier 2 solely because the register's threat model assumes an English-speaking guild. For
  any non-English deployment it is a Tier-0 S2 with a very cheap core fix.
