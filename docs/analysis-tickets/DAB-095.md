# DAB-095: `sqlite_utils` sets no PRAGMAs — no WAL, implicit busy timeout, foreign keys off

> **PARTIALLY DONE — the busy timeout landed in Phase 4; WAL is deliberately DEFERRED.**
>
> WAL made **no difference** to the failure this ticket is cited as fixing: the real
> `upsert_message` under a six-second lock returned `False` at ~5008 ms in *both* journal modes and
> succeeded at ~6036 ms in both once the timeout rose. It also costs **+0.34 ms on every SQLite
> call** here (0.230 -> 0.573 ms), because the cost is WAL's per-call *connect*, and this
> architecture opens a connection per call -- which this ticket itself notes in one line before
> recommending the pragmas anyway.
>
> The headline "5.01 s -> 3.3 ms" reproduces only against `BEGIN EXCLUSIVE`; against `BEGIN
> IMMEDIATE` a read succeeds in 0.1 ms in both modes.
>
> **Reopen WAL when connections are pooled.** Landed instead: `bot.sqlite_busy_timeout_ms`, default
> **5000 ms** -- the value already in force -- because the stated defect is that the timeout is
> "not a stated contract and cannot be tuned", and because raising it trades a failed write for a
> longer event-loop stall while most SQLite calls still run on the loop.
>
> `synchronous` was **not** split per database: FULL is already the sqlite3 default, so the "split"
> would only be an opt-in NORMAL for the RAG database, and `token_usage.db` has five owners, not
> the two the ticket implies. See [`ANALYSIS_CORRECTIONS.md`](../ANALYSIS_CORRECTIONS.md) item 14.
> Guarded by `M-DAB095` and `M-DAB095B`.

- Type: IMPROVEMENT
- Severity / Payoff: S2. Measured: a contended read **fails after 5.01 s -> succeeds in 3.3 ms**;
  write throughput **2,918 -> 12,355/s (4.2x)**
- Effort: S — ~15 lines in one file

## Context

`sqlite_utils.sqlite_connection` is, per `AGENTS.md`, "the only `sqlite3.connect` site under
`src/`". It takes no pragma configuration and exposes no hook for one.

Six separate findings share this root cause: the designated single seam for database access is too
thin to carry the invariants that belong there. It owns connection lifetime and nothing else. 4 of 7
services expand `~`, 2 of 7 create their parent directory, 1 of 6 has a column-upgrade path, and
**0 of 7 set a pragma.**

## Evidence

`src/services/sqlite_utils.py:13-32` — the whole function:

```python
13: @contextmanager
14: def sqlite_connection(
15:     db_path: DatabasePath,
16:     *,
17:     row_factory: Optional[RowFactory] = None,
18: ) -> Iterator[sqlite3.Connection]:
19:     """Open a connection that rolls back on failure and always closes."""
20:     connection = sqlite3.connect(db_path)
21:     if row_factory is not None:
22:         connection.row_factory = row_factory
23:     try:
24:         yield connection
25:     except BaseException:
26:         try:
27:             connection.rollback()
28:         except sqlite3.Error:
29:             pass
30:         raise
31:     finally:
32:         connection.close()
```

Measured pragma values on a helper-produced connection (`/tmp/b5probe/p1_pragmas.py`):

```
  PRAGMA journal_mode   = delete
  PRAGMA busy_timeout   = 5000
  PRAGMA foreign_keys   = 0
  PRAGMA synchronous    = 2
  connection.isolation_level = ''

=== 1c. Two concurrent writers ===
  second writer outcome: {'err': 'OperationalError: database is locked', 'elapsed': 5.01}

=== 1e. foreign_keys off: orphan rows are accepted ===
  orphan child rows accepted: [(1, 999)]

=== 1g. a slow writer starves everyone past the 5s busy_timeout ===
  set_personality returned: False
  channel_settings rows persisted: [(1,)]     # channel 2 never landed
```

One wording correction worth carrying: there **is** a busy timeout — 5000 ms, Python's
`sqlite3.connect` default. `sqlite_utils.py` never sets it, so it is implicit and undocumented, but
it exists. The defect is that it is not a stated contract and cannot be tuned.

The measured payoff:

```
with a write lock held:
  rollback-journal read   FAILS after 5.01 s
  WAL read                OK in 3.3 ms
  single-row write throughput  2,918 -> 12,355/s  (4.2x)
```

Silent loss past the timeout (`/tmp/b4probes/p11_e2e_quality.py`):

```
11c. Lock starvation past the 5 s default busy_timeout
  upsert_message during a 6 s exclusive lock -> returned False after 5.01 s
  is message 99 in the index? False
```

**Honest counter-evidence that must survive into the ticket.** At *moderate* concurrency with short
transactions the current design holds up: 16 threads x 40 rounds x 4 writes across all four
token-DB services produced **0 errors, 640/640 rows in every table, 1146 writes/s**. And one claim
in the original lead does **not** hold — a writer does not block readers here (a reader completed
in 0.00 s); SQLite readers proceed against a RESERVED lock until COMMIT. The reader-starvation
argument for WAL is weaker than the writer-starvation one. This is a latent risk that materialises
with a long transaction or a slow disk, not an immediate breakage.

A separate measurement changes how you should sequence this: **0.265 ms of pure connect overhead per
query against 0.029 ms of actual work — the connect is 9x the query.** Adding the pragmas to a
per-call connection costs a further **+0.322 ms**. Per-call connections and correct pragmas are
mutually exclusive at any sane cost.

The shape:

```python
connection = sqlite3.connect(db_path, timeout=<configured>)
connection.execute("PRAGMA journal_mode=WAL")
connection.execute("PRAGMA busy_timeout=<configured_ms>")
connection.execute("PRAGMA synchronous=<NORMAL|FULL per database>")
connection.execute("PRAGMA temp_store=MEMORY")
```

`journal_mode` is persistent per database file; the rest are per-connection.

**Two values are disputed between lanes. Decide before writing the test.**

| Pragma | Lane B5 | Lane I2 |
|---|---|---|
| `busy_timeout` | 30000 ms | 5000 ms explicit, 15000 ms on the writer connection |
| `synchronous` | `NORMAL` everywhere | `FULL` on `token_usage.db` (billing-adjacent), `NORMAL` on `message_rag.db` (reconstructible) |

The split-`synchronous` argument is the stronger one: `NORMAL` measured 12,355 -> 12,626 writes/s,
i.e. **+2%, noise**, so this is a durability decision rather than a performance one, and
`token_usage.db` is the one you cannot rebuild.

Two more from the same design, worth taking: `cache_size = -16000` (16 MB) on reader connections
once they are long-lived, and **leave `mmap_size` off** — it turns an I/O error into a SIGBUS
instead of a Python exception.

## Risks and notes

- **Five WAL implications, all of which belong in the commit message:**
  1. Readers stop being collateral damage. Measured under a sustained write burst with WAL and a
     4-thread reader pool: median 0.206 ms, p95 0.304 ms, max 0.410 ms, **zero `SQLITE_BUSY`**.
  2. Readers see a snapshot, not the newest commit. Harmless here — the RAG path is best-effort and
     already degrades silently.
  3. A long-lived reader pins the WAL. **Rule to enforce: never hold a read transaction open across
     an `await`.**
  4. Three files, not one. `-wal` and `-shm` appear beside the database. Any backup that copies only
     the `.db` now silently loses the tail.
  5. **WAL does not help writers.** Measured: a second writer still fails after 5.01 s in WAL mode.
     `DAB-065` still needs its own semantics fix.
- **Do not enable `foreign_keys=ON` in this ticket.**
  `message_embeddings.message_id REFERENCES message_index(message_id)` (`:174`) is decorative today,
  and `delete_rag_data` (`:933-943`) hand-orders its deletes to compensate. Turning FKs on without
  `ON DELETE CASCADE` means orphans predating the change start raising. Gate it on `I2-11`.
- **One existing test pins the current broken behaviour and is at risk if you also add `mkdir` to
  `sqlite_connection`:** `tests/test_sqlite_services.py:174-205`
  `test_services_preserve_directory_creation_and_fallback_policies` asserts
  `self.assertFalse(missing_parent_db.parent.exists())` at `:205` and wraps four service
  constructions in `with self.assertLogs(level="ERROR")` at `:187`. That is `DAB-101`'s territory;
  keep it out of this ticket.
- Other tests in the blast radius (all drive the same seam):
  `tests/test_sqlite_services.py:23-34` (asserts `sqlite3.ProgrammingError` on a closed connection
  at `:33-34` — a pragma executed before the `yield` must not change that);
  `tests/test_sqlite_services.py:36-52` (asserts rollback leaves `COUNT(*) == 0` at `:50` — a pragma
  must not open a transaction); `tests/test_sqlite_services.py:214`;
  and the whole of `tests/test_message_rag_services.py` and `tests/test_rag_optimization.py`.
  `tests/test_rag_optimization.py:94` is separately flagged by `AGENTS.md` as a flaky negative-timing
  assertion, and pragma changes shift real timings — expect it to be the first thing that flakes.
- `journal_mode=WAL` is persistent in the file header: one `PRAGMA` on first open and it sticks.
  Rollback is `PRAGMA journal_mode=DELETE` with no other connection open — do that in an offline
  maintenance script, not in the running bot.
