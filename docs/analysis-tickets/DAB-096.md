# DAB-096: Synchronous SQLite runs on the asyncio event loop at 13 call sites

- Type: IMPROVEMENT
- Severity / Payoff: S2. Max event-loop stall **4,997.3 ms -> 3.1 ms**. Per call 0.258 ms inline ->
  0.089 ms via a warm pooled thread (faster, because the 0.265 ms connect disappears).
- Effort: M — S per site, 13 sites; sites 1 and 12/13 are most of the payoff
- Priority score: 6.0 — impact High (3) x frequency Continuous (4) / effort M (2)
- Confidence: **VERIFIED** — loop-stall measured directly through the real service
- Merged IDs: `B5-02`, `B4-13`; the call-site inventory and design are `I2-07`
- Blocks / Blocked by: blocked by `DAB-095` (the pragmas resolve contention rather than timing out).
  Best after a bounded executor; `asyncio.to_thread` is a valid interim.

## Context

`ChannelSettingsService`, `UserPreferencesService`, `MessageVisibilityService`, `PinService` and
`ReportService` expose only blocking methods, and every caller is an `async def` coroutine that
invokes them directly. `TokenTracker` is the sole service that offloads to a thread.

So when the 5 s busy timeout elapses, it elapses **on the event loop**. The whole bot — including
the gateway heartbeat — freezes.

The omission is inconsistent rather than deliberate: `HybridContextRetriever._load_pins`
(`hybrid_context_retriever.py:447`) *does* use `to_thread`, and `MessageIndexService` provides
`mark_deleted_async` and `index_discord_message_async`. There is no `mark_hidden_async`.

Sites 6, 7 and 9 are the sharp ones: they sit inside `for` loops over candidate messages, so one

the report web server shares the bot's event loop, so a report page view stalls Discord.

`_ensure_table` / `_ensure_schema` at construction also block, but that is startup and is covered by
`DAB-077`.

Measured loop stall (`/tmp/b5probe/p1h_loopstall.py`) — a background thread holds a write
transaction, then a coroutine calls `set_personality` exactly as `personalization.py:59` does:

```
  set_personality() blocked the calling coroutine for 5.01s (returned False)
  worst event-loop heartbeat gap during that window: 5.01s
```

Independently: **max loop gap 4997.3 ms inline vs 3.1 ms offloaded.**

Uncontended cost of the same calls (`/tmp/b4probes/p10_backfill_contention.py`):

```
  PinService.add_pin()           : 0.576 ms  (sync in /pin callback, personalization.py:180)
  PinService.get_pins(200 pins)  : 0.477 ms  (sync in /pins callback, personalization.py:205)

  MessageIndexService.mark_hidden: 0.324 ms  (sync in the /hide and /unhide loops, :273/:347)
  /hide iterates up to 10 messages -> 10 synchronous write transactions on the loop.
```

For `_is_live_mode_enabled` specifically, at 50,000 messages/day the offload reclaims 12.9 s/day of
loop time on the happy path — and eliminates a whole-bot freeze on the unhappy one.

**Which offload mechanism.** Four were compared:

| Option | Verdict |
|---|---|
| `asyncio.to_thread` / default executor | What most of `message_index_service` already does. Measured +0.139 ms wall. Unbounded (`min(32, cpu+4)` workers) so it can fan 32 concurrent writers into a 5 s lock pile-up. **Fine as the interim step, wrong as the destination.** |
| Bounded executors with thread-local connections | **Recommended.** Same `run_in_executor` API, bounded, writes serialised. Measured 0.089 ms median. |
| Dedicated thread + queue | Equivalent to a 1-worker executor with hand-rolled futures. Measured identical. Rejected: more code, no gain. |
| `aiosqlite` | New dependency requiring a `constraints.txt` regeneration from a clean 3.12 env. Internally it *is* thread-per-connection with a queue. Its real value is `async with`/`async for` ergonomics, which would mean rewriting ~30 call sites. **Rejected: pays a dependency and a rewrite for syntax.** |

Ship `to_thread` first if the bounded executor slips; each site is an independent one-line change.

## Test to add

`EventLoopBlockingTest(IsolatedAsyncioTestCase)`:

```
test_channel_settings_write_does_not_block_loop:
    patch sqlite_transaction to sleep 0.5 s
    run an async heartbeat task with asyncio.sleep(0.01) ticks
    drive the /live callback
    assert the maximum observed tick gap stays under 0.1 s

test_pin_and_mark_hidden_run_off_the_main_thread:
    patch PinService.add_pin / MessageIndexService.mark_hidden with a function that asserts
      threading.current_thread() is not the main thread
    drive the command callbacks
    assert the check passed
```

The second is preferable — it is deterministic where the first is a timing assertion, and
`AGENTS.md` already flags one flaky timing test in this suite.

If a call site regresses to a synchronous call, the thread-identity assertion fails.

## Risks and notes

- **Count discrepancy to resolve:** the master register's title says **9** call sites; the
  authoritative inventory above lists **13**; a third source lists 5. Use the 13-row table — it is
  the most recent and most granular.
- Risks per option: `to_thread` everywhere risks unbounded fan-out (32 threads piling into one 5 s
  lock wait); a bounded executor risks a slow query behind 2 reader slots queueing the rest — which
  `DAB-078` mitigates by making the reads sub-millisecond, and which is handled by routing
  `get_status` and `delete_rag_data` to the writer lane.
- `tests/test_command_registration.py` pins the tree by `callback_name`. Converting a callback to
  `async` does not change its name, so `EXPECTED_SIGNATURE` should hold — **but re-run it.**
  `:184-185` also asserts `_pin_service` and `_message_visibility_service` are attached; wrapping
  them changes what is attached.
- Existing tests calling the **sync** methods directly, which is why they must be retained:
  `tests/test_sqlite_services.py:125-135` (`add_pin`/`get_pins`/`delete_pin`/`get_pins_for_prompt`),
  `:75` (`MessageVisibilityService`), `:214` (the `TokenTracker` model to copy), and the whole of
  `tests/test_report_service.py` for sites 10-13.
- `mark_hidden` moving onto a worker thread does **not** remove the lost-update race on `hidden`
  (`DAB-069`) — it just changes its shape. Land the atomic `ON CONFLICT` form from `DAB-065`
  alongside.
- Rollback is per site; each is an independent one-line change.
