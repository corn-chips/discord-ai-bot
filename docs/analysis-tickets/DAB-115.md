# DAB-115: `split_message` is O(n^2) and runs synchronously on the event loop

**Status: LANDED** in `b0d8308` — a single parse plus a bisect index; 802x on a 139 KB fenced block, 192/192 outputs byte-identical, growth now linear. The event-loop half is untouched: `split_message` is still called synchronously from `response_delivery.py:281` (TD-017).

- Type: BUG
- Severity / Payoff: **S1** — the corpus's only ordinary-traffic stop-the-world stall.
  Improvement payoff: **1088x** measured (59.96 s -> 0.055 s at 234 KB), 192/192 outputs
  byte-identical
- Effort: S — one 35-line helper class, one parameter threaded through three methods
- Priority score: 12.0 — impact Critical (4) x frequency Common (3) / effort S (1)
- Confidence: **VERIFIED** by three independent measurements
- Merged IDs: `B6-05`, `C5-03`; fix prototyped as `I3-01`
- Blocks / Blocked by: none. "Land this first" per the performance lane.

## Context

`MessageSplitter._find_next_split_point` walks candidate break points in five priority tiers and
calls `markdown_parser.is_safe_split_point(content, split_pos)` for **each candidate**.
`MarkdownParser.is_safe_split_point` does a full `find_code_block_boundaries(text)` **and** a full
`parse_markdown(text)` — ten `finditer` passes over the *entire* document — every time.

With ~2 KB windows and up to a few hundred candidates per window, an N-byte message triggers
Theta(N^2 / 2000) full-document parses. It runs synchronously on the event loop, so the gateway
heartbeat, every other channel, every command and the shutdown path all stop.

The trigger is a message length, not a corpus size. An ordinary "write me this program" answer does
it.

## Acceptance criteria

- [ ] `split_message` builds the parse **once per call** into a `_SplitIndex`:
      - `code_boundaries` — the single `find_code_block_boundaries` result, reused by tier 2 and by
        `_preserve_code_blocks` (which re-scans at `:383` today).
      - an interval index of every span `is_safe_split_point` rejects (code blocks + the six inline
        formatting types), sorted by `start` with a **prefix-max of `end`**. `is_safe_split_point(p)`
        becomes exactly `not exists interval: start < p < end`, answered by one `bisect_left` plus
        one comparison.
- [x] Output is byte-identical across the equivalence corpus, which landed at 192 cases, not 131.
- [ ] A 120 KB fenced-code input splits in well under 1 s (measured 0.0275 s in the prototype).
- [ ] `find_code_block_boundaries` is called O(parts), not O(candidates).
- [ ] `markdown_utils.py` is **untouched** — its `is_safe_split_point` stays for other callers.
- [ ] The **strip-table** optimisation is explicitly NOT included (see Risks).

## Files to touch

## Risks and notes

- **Ship the interval index only.** The original prototype also replaced
  `len(content[a:b].strip())` with O(1) precomputed non-whitespace neighbour tables. Measured, that
  made things *worse*: at 176 KB, code_heavy went 0.0265 s (index only) -> 0.0533 s (index + strip
  tables); one_giant_code_block 0.0414 -> 0.0649. 120,000 `str.isspace()` calls cost more than the
  slicing they eliminate. `/tmp/i3-perf/fast_splitter.py` is the rejected fuller variant;
  `/tmp/i3-perf/fast_splitter_final.py` is the one to port.
- **One accepted regression:** `no_whitespace` at 120 KB goes 0.0156 -> 0.0305 s (0.5x). Text with
  no whitespace has almost no candidates, so the shipped code barely re-parses while the prototype
  still pays one O(n) index build. Absolute cost is 30 ms and growth is linear.
- **The one thing to watch:** the index must be built from the *same* string the split points index
  into. The prototype builds it from `stripped_content`, matching the shipped code exactly.
- **Existing tests in the blast radius** (all must stay green; the 131/131 equivalence check is the
  reason they will):
  - `tests/test_bug_regressions.py:18-33`
    `MessageSplitterRegressionTest.test_long_fenced_line_is_lossless_and_within_discord_limit` —
    content is ``` "```python\n" + ("x" * 5000) + "\n```" ``` at `:20`, exactly the worst-case shape;
    asserts losslessness at `:32` and `validate_split_integrity` at `:33`.
  - `tests/test_discord_orchestration.py:233-256` `ResponseDeliveryCoordinatorTest.make_delivery`
    builds a real `MessageSplitter`.
  - `tests/test_discord_orchestration.py:258-294` asserts `len(view.pages) > 1` at `:286`.
  - `tests/test_discord_orchestration.py:296-318` pins byte-exact chunks `["abc", "def", "gh"]`
    from `split_length=3`.
  - `tests/test_discord_orchestration.py:320-330` covers the whitespace-only input path.
- The broader lane also proposed bounding candidate iteration (stop after the first K failures) and
  capping accepted response length before splitting. Both are reasonable follow-ups; neither is
  needed for the 1088x and both change output, which would break the equivalence guarantee.
