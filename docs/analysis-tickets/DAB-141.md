> **STATUS: the permission gate LANDED, and this ticket's prescribed form of it was wrong.**
>
> Applying `@app_commands.default_permissions(...)` to the `/rag delete` **subcommand**, as the
> sections below describe, produces a gate that protects nothing. discord.py serialises permissions
> only at the top level of the command tree: the decorator sets the local Python attribute, but
> `to_dict()` drops it and Discord receives `default_member_permissions: null` — byte-identical to
> having no gate at all. Verified on discord.py 2.7.1. The acceptance test proposed below reads the
> *attribute*, so it would have passed on the broken fix.
>
> What landed instead: `default_permissions=Permissions(manage_guild=True)` plus `guild_only=True`
> on the **group** (payload `32`, `dm_permission: false`), *and* a runtime `_has_rag_admin` check
> inside the callback. Both are needed. The payload permission is a default that a guild admin can
> re-grant from the integrations UI, and Discord does not evaluate it outside a guild at all, so
> for an unrecoverable delete it cannot be the only barrier.
>
> Consequences for the rest of this ticket: a group-level gate does **not** populate `.checks`, so
> the `checks == []` assertion at `tests/test_command_registration.py:176` survives untouched, as do
> the counts at `:147-148` and the `[5:10]` slice at `:239`. The gate covers all three subcommands,
> which is deliberate rather than collateral: `/rag backfill` triggers an unbounded history scan
> billed to the operator's own key, and `/rag status` reports the host database path.
>
> Still open from the sections below: the `guild_id` predicate in `message_index_service`, the
> confirmation view, the actor log, and the description text that omits pins.
> See [`../ANALYSIS_CORRECTIONS.md`](../ANALYSIS_CORRECTIONS.md) item 3.

## Context

`/rag delete` carries no permission decorator, no confirmation step, and no guild predicate. Any
guild member — including in a DM, since `guild_only=False` on every command in the tree — can
select `scope: All channels` and truncate six tables across **every guild the bot serves**.

The message index can in principle be rebuilt from Discord history via `/rag backfill`.
`pinned_messages` cannot: pins are user-authored memories created via `/pin` and stored **only** in
`message_rag.db`. There is no upstream source of truth. That is unrecoverable user-data destruction
by an unprivileged caller.

The codebase demonstrably knows the mechanism: `/clear-cache`, which only clears an in-memory
metrics cache, carries `@app_commands.default_permissions(administrator=True)` at
`configuration.py:322`.

## Evidence

- Command: `src/bot/command_modules/research.py:242-289`. The decorator stack is `@rag_group.command`
  (`:242`), `@app_commands.describe` (`:243`), `@app_commands.choices` (`:244-247`) — and nothing
  else. The `rag` group itself (`research.py:140`) is likewise unguarded.
- `scope` choice `"all"` at `:246`; `channel_id = None` at `:267`.
- The callback never inspects `interaction.user`; it goes from `response.defer()` (`:266`) straight
  to `delete_rag_data_async(channel_id=None)` (`:272-274`).
- The only guard, `:259-264`, applies to `scope == "channel"` only.
- The global delete branch: `src/services/message_index_service.py:883-912`.

```python
if channel_id is None:
    deleted_messages = conn.execute("SELECT COUNT(*) FROM message_index").fetchone()[0]
    if self.fts_enabled:
```

Six unqualified `DELETE`s, no `guild_id` predicate anywhere, against a single shared
`data/message_rag.db`. It also first calls `retriever.cancel_background_work(channel_id=None)`
(`research.py:271`), cancelling in-flight indexing everywhere.

Runtime probe of the real tree (`/tmp/v1probes/p10_rag_delete_perms.py`), built via the actual
`setup_commands`:

```
rag delete     default_permissions=None            checks=[] guild_only=False
clear-cache    default_permissions=<Permissions value=8>  checks=[] guild_only=False

rag GROUP default_permissions: None | guild_only: False
  callback mentions 'permission':     False
  callback mentions 'administrator':  False
  callback mentions 'confirm':        False
  callback mentions 'guild_id':       False
  callback mentions 'interaction.user': False

  any guild filter in delete_rag_data?: False
```

`Permissions value=8` is `administrator`; `None` means Discord exposes the command to `@everyone`.

A second independent pass confirmed `to_dict()` ships `dm_permission=True` for every node, so the
command is invocable in a DM where there is no guild to evaluate permissions against at all.

Observable symptom: the bot stops recalling anything. Because RAG failures degrade silently to the
legacy `ContextCollector` path with only a warning, this reads as "the bot got dumber" rather than
"someone deleted the database". There is no server-side log of *who* did it — `research.py:284-289`
logs nothing about the actor.

## Reproduction

Invoke `/rag delete` with `scope: All channels` as any unprivileged guild member, or in a DM.
`channel_id` resolves to `None` at `research.py:267`, selecting the unqualified branch.

## Acceptance criteria

- [ ] `/rag delete` (or the whole `rag` group) carries a permission gate. `manage_guild` is the
      proportionate choice; `administrator` matches the existing `/clear-cache` precedent.
- [ ] `@app_commands.guild_only()` is applied so the command cannot be invoked in a DM.
- [ ] `scope: all` means "all channels **in this guild**": a `guild_id` is threaded down and
      `delete_rag_data` deletes `WHERE guild_id = ?`. A genuinely global wipe becomes an operator
      CLI action under `scripts/`, not a slash command.
- [ ] The destructive scope requires a confirmation interaction — a `discord.ui.View` with a danger
      button and an `interaction_check` pinning it to the invoker.
- [ ] The actor is logged at WARNING with user id, guild id, scope, and row counts.
- [ ] The command description tells the truth about pins. "Delete stored message RAG data" does not
      say that every pinned memory dies too.

## Risks and notes

- **Four existing assertions break. This is the sharpest test collision in the backlog.**
  - `tests/test_command_registration.py:175-176` —
    `for path in ("rag status", "rag backfill", "rag delete"): self.assertEqual(self._command(bot, path).checks, [])`.
    This **explicitly pins that `/rag delete` has no checks.** Any `app_commands.check` makes
    `.checks` non-empty. Note that `@app_commands.default_permissions(...)` does *not* populate
    `.checks`, so choosing `default_permissions` over a `check` avoids this one collision — decide
    deliberately, and update the assertion either way, because pinning "this command is ungated" is
    itself the bug.
  - `tests/test_command_registration.py:48` — `EXPECTED_SIGNATURE` pins
    `("rag delete", "Delete stored message RAG data", "rag_delete")` byte-for-byte. Renaming the
    description breaks it.
  - `tests/test_command_registration.py:167-170` — pins the two scope choices.
  - `tests/test_command_registration.py:187-215`
    `test_rag_delete_scopes_deletion_and_stops_background_work` calls the callback at `:204-207`
    with a bare `SimpleNamespace` interaction (`:197-201`) that has **no `user` attribute**. Any
    gate reading `interaction.user.guild_permissions` raises `AttributeError` there. It also asserts
    `delete_rag_data_async.assert_awaited_once_with(channel_id=20)` at `:213-215`, so adding a
    `guild_id=` kwarg breaks the exact-call assertion.
  - `tests/test_command_registration.py:173` — `self.assertTrue(clear_cache.default_permissions.administrator)`
    is the template for how a gated command is asserted. Copy that shape for `/rag delete`.
- The existing test `test_rag_delete_scopes_deletion_and_stops_background_work` pins the
  global-wipe *behaviour* as intended and asserts nothing about permissions — so this is an
  unguarded gap, not a guarded one anyone missed.
- Landing the permission gate alone (no description change, no guild predicate) is a legitimate
  first commit and only touches `:175-176` and `:187-215`. Do that in Sprint 1; defer the scoping
  and copy changes until `DAB-203` has de-brittled the tree test.
