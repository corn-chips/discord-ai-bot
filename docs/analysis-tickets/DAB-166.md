# DAB-166: `/config debug` is a no-op; handler levels are pinned at startup

- Type: BUG
- Severity / Payoff: S2
- Effort: S
- Priority score: 6.0 — impact High (3) x frequency Occasional (2) / effort S (1)
- Confidence: **VERIFIED** — probe shows the toggle raising the logger level while every handler
  stays at INFO
- Merged IDs: `B8-03`
- Blocks / Blocked by: none, but it **gates** every other ticket whose diagnosis says "check the
  debug logs". Until this is fixed, no DEBUG line in the codebase is reachable in a default
  deployment.

## Context

`setup_logging` pins each handler's level at startup. `/config debug` raises the **logger's** level
and nothing else. A record must clear *both* gates: the logger now says yes, every handler still
says no.

The command then reports success, telling the operator they have already looked when they have not.

This is the *only* runtime lever an operator has over the 39 `except` handlers that are invisible at
the default log level (`DAB-169`). Fix the observability tools before relying on them.

## Evidence

- Handler pinning: `src/utils/logging_config.py:439` (console) and `:456` (file).

```python
439:         console_handler.setLevel(numeric_level)
456:         file_handler.setLevel(numeric_level)
```

- What the command actually does: `src/bot/command_modules/configuration.py:153-156`.

```python
153:         root_logger = logging.getLogger()
154:         if enabled:
155:             root_logger.setLevel(logging.DEBUG)
```

- The false success message: `configuration.py:166`.

```python
166:             description=f"Logging level set to {'DEBUG' if enabled else 'INFO'}.",
```

Trigger: always, with any `log_level` above `DEBUG` — i.e. the shipped default
`config.yaml` `logging.level: "INFO"` (line 21).

B8 probe (`/tmp/b8probe/p8_debug_noop.py`):

```
after setup_logging(log_level='INFO'):
  root.level          = INFO
  handler RotatingFileHandler    .level = INFO

--- now do EXACTLY what /config debug does (configuration.py) ---
  root.level          = DEBUG
  handler RotatingFileHandler    .level = INFO           <- unchanged
  lg.isEnabledFor(DEBUG) = True   <- logger says YES

--- CONTENTS OF /tmp/b8probe/p8/bot.log ---
  ... | src.utils.logging_config    | Logging configured - Level: INFO, ...
  ... | src.bot.rag_event_coordinator | INFO before toggle
  ... | src.bot.rag_event_coordinator | INFO after toggle
```

The two `logger.debug(...)` calls — including one **after** the toggle — are absent.

Observable symptom: an operator runs `/config debug enabled:True`, sees "Debug Mode Enabled —
Logging level set to DEBUG", and **no additional log lines ever appear**. The only way to see DEBUG
output is to edit `config.yaml` and restart.

A second, separate defect the same command has: it mutates the logger but not `config.log_level`,
so `/config info` and any other reader of the config still report the old level.

## Reproduction

```python
import logging
from src.utils.logging_config import setup_logging
setup_logging(log_level="INFO", log_file="/tmp/x/bot.log", enable_console=False,
              enable_performance_logging=False)
logging.getLogger().setLevel(logging.DEBUG)      # exactly what /config debug does
logging.getLogger("x").debug("visible now")
logging.shutdown()
# "visible now" is absent from /tmp/x/bot.log
```

## Acceptance criteria

- [ ] After `/config debug enabled:True`, a `logger.debug(...)` call anywhere reaches the log file
      and the console.
- [ ] After `/config debug enabled:False`, DEBUG records stop appearing.
- [ ] `config.log_level` is updated to match, so `/config info` and any other reader report the
      truth.
- [ ] The success message is only sent when the change actually took effect.

## Files to touch

- `src/utils/logging_config.py` — `:439` (console handler level), `:456` (file handler level). The
  performance handler wiring at `:462-476` is adjacent (`DAB-171`, `DAB-172`).
- `src/bot/command_modules/configuration.py` — `:153-156` (the toggle), `:166` (the success copy).

Two options, both cheap:

1. **Preferred:** stop pinning handler levels in `setup_logging`. Drop
   `console_handler.setLevel(...)` and `file_handler.setLevel(...)`; a handler at `NOTSET` (0)
   passes everything the logger allowed. Level policy then lives in exactly one place.
2. Make `/config debug` walk the handlers too:

```python
target = logging.DEBUG if enabled else logging.INFO
root_logger.setLevel(target)
for h in root_logger.handlers:
    h.setLevel(target)
```

Option 1 is structurally better and removes a whole class of "the level is set in two places"
confusion. Option 2 is smaller. If you take option 1, verify the performance handler at `:476` still
gets the level it needs — `performance_*.log` is already always 0 bytes for a different reason
(`DAB-172`, the configured logger name is orphaned).

## Test to add

`tests/test_logging_config.py` (new file — this module has zero coverage today), class
`LoggingLevelTest`:

```python
def test_raising_root_level_at_runtime_reaches_handlers(self):
    with tempfile.TemporaryDirectory() as d:
        lf = os.path.join(d, "bot.log")
        setup_logging(log_level="INFO", log_file=lf, enable_console=False,
                      enable_performance_logging=False)
        logging.getLogger().setLevel(logging.DEBUG)
        logging.getLogger("x").debug("visible now")
        logging.shutdown()
        self.assertIn("visible now", open(lf).read())
```

Second test: drive the `/config debug` callback directly and assert `config.log_level` was updated.

If the defect returns, the first assertion fails because the file does not contain `visible now`.

## Risks and notes

- **No existing test breaks.** `configuration.py`'s command surface is pinned by
  `tests/test_command_registration.py`, but only by path, description and callback name — none of
  which changes here. Re-run it anyway.
- Removing handler-level pinning means the root logger level becomes the single gate. If any code
  path relies on a handler being *quieter* than the logger, that behaviour changes. Grep for
  `setLevel` across `src/` before choosing option 1.
- Enabling DEBUG at runtime will now actually produce DEBUG output, including the 39 handlers
  catalogued in `DAB-169` and the live-mode RAG failure at `DAB-168`. That is the point, but it
  means the first operator to use the fixed command will see a lot of new noise. Say so in the
  command's response text.
- Land with `DAB-165`. Together they make the log file trustworthy, which every other ticket's
  "check the logs" instruction depends on.
