# DAB-180: `grok-prompts` is a dangling submodule gitlink, so `/deepresearch` silently uses a stub prompt

**Status: OPEN** — `grok-prompts` is still a dangling gitlink and `/deepresearch` still degrades silently.

- Type: BUG
- Severity / Payoff: S2
- Effort: S
- Priority score: 8.0 — impact Medium (2) x frequency Continuous (4) / effort S (1)
- Confidence: **VERIFIED** — reproduced with a genuine fresh clone and by replaying the template
  block
- Merged IDs: `C3-01`, `C3-02`, `C3-03`, `C6-20`; the fresh-clone half is `I6-11(b)`
- Blocks / Blocked by: **blocked by `DAB-203`** *if* the fix makes `/deepresearch` refuse to
  register when the template is missing — that changes the command tree and breaks
  `EXPECTED_SIGNATURE`, the `== 22` / `== 35` counts, and possibly the `[5:10]` slice.

## Context

`grok-prompts` is committed as a gitlink (mode `160000`) with no `.gitmodules` entry and a target
object that is not in the object database. A fresh clone gets an **empty directory** and a clean
`git status`.

`/deepresearch` hard-depends on one file inside it, catches the resulting `FileNotFoundError`,
substitutes a one-line stub prompt, tells the user nothing, and still spends a full
high-complexity synthesis call.

Separately, the "fallback" path lookup in that same block is a no-op that resolves to the identical
file.

An unregistered gitlink is never correct.

Fresh clone:

Introduced by commit `7d88b0e` ("added grok prompts"). Because `git status` is clean, this is easy
to miss. Any clone with `--recurse-submodules`, or any CI/tooling step that runs `git submodule`,
errors out.

The consumer, `src/bot/command_modules/research.py:76-101`:

```python

            template_path = os.path.join("grok-prompts", "default_deepsearch_final_summarizer_prompt.j2")
            if not os.path.exists(template_path):

                template_path = os.path.join(os.getcwd(), "grok-prompts", "default_deepsearch_final_summarizer_prompt.j2")

            try:

                final_prompt = template.render(

                    current_time=..., language="English", prefill=False,

                    real_time_data_provider_called=False,
                    contains_url=True,
                    supported_inline_rich_content_tools=False

            except Exception as e:
                logger.error(f"Template error: {e}")

```

Exact lines: `template_path = os.path.join("grok-prompts", ...)` at `:77`;
`if not os.path.exists(template_path):` at `:78`; the "fallback" reassignment at `:80`;
`with open(template_path, ...)` at `:83`; `template = jinja2.Template(...)` at `:86`;
`logger.error(f"Template error: {e}")` at `:99`; the stub prompt at `:101`.

**The fallback is a no-op.** A bare relative path is *already* resolved against `os.getcwd()`, so
line `:80` resolves to the identical file. The comment claims it handles "running from different
cwd"; it does not. There is no `Path(__file__)`-anchored lookup anywhere.

The stub throws away every variable the template was designed to receive (`current_time`,
`language`, `prefill`, `contains_url`, `supported_inline_rich_content_tools`) and still spends a
full high-complexity synthesis call.

Symptom for a new user: `/deepresearch` "works" but the reports are noticeably generic. The only
trace is one `ERROR Template error: ...` line in the console log, on **every** invocation.

Documentation that assumes the directory is populated: `docs/BOT_SYSTEM_REPORT.md:81` and `:530`
describe it as holding several `.j2` prompt assets. Nothing tells a new user where to get them, and
no recovery command exists.

## Acceptance criteria

- [ ] The gitlink is resolved one way or the other. **Recommended: commit the `.j2` assets as
      ordinary tracked files and drop the gitlink** (`git rm --cached grok-prompts`, then add the
      files) — `/deepresearch` hard-depends on one specific filename. The alternatives are a proper
      `.gitmodules` with a real URL, or deleting the entry and inlining the template.
- [ ] `git submodule status` no longer prints `fatal:`.
- [ ] `git clone --recurse-submodules` succeeds.
- [ ] The template path is anchored on the package —
      `Path(__file__).resolve().parents[3] / "grok-prompts" / ...` — or becomes a `config.yaml`

- [ ] A missing template is **loud**: checked once at registration time, producing either a refusal

      say so in the log.

## Risks and notes

- **No existing test covers `/deepresearch`'s template load.**
  `tests/test_command_registration.py` pins
  `("deepresearch", "Perform a deep research task and generate a report", "deepresearch")` in
  `EXPECTED_SIGNATURE` — i.e. only that the command is *registered*, never that its template
  resolves. **If the fix makes `/deepresearch` refuse to register when the template is missing, that
  changes the command tree and WILL break `EXPECTED_SIGNATURE`, the `== 22` / `== 35` counts, and
  possibly the `[5:10]` slice.** That is the dependency on `DAB-203`. The WARNING option avoids the
  collision entirely and is the safer first move.
- **Removing the gitlink is a history/intent question.** One source rates it "needs-care — confirm
  with the author before removing", and the dead-code sweep deliberately held it *out* of its
  cleanup commit for that reason. Do not `git rm --cached` without asking whether the upstream
  repository still exists.
- Four sibling fresh-clone problems belong to the same ticket family and are cheap to fold in:
  `start.sh` is committed `100644` (`git update-index --chmod=+x start.sh`); a partial install
  poisons `.venv` (build into `.venv.tmp` and `mv` on success — that is `DAB-181`); the interpreter
  probe diverges between `start.sh` (3 probes) and `start.bat` (2); both scripts reinvent
  `__pycache__` cleanup instead of calling `scripts/cleanup_pycache.py`; and `.gitignore` has
  `!.env.example` for a file that does not exist.
- Explicitly **not** worth doing: a `config.yaml.example`. `config.yaml` is tracked with working
  defaults, so an example file would create a second source of truth that drifts. (Note the
  missing-config error message points at `config.yaml.example` today, and a test pins that string —
  that is `DAB-188`, a separate fix.)
- `jinja2` is imported in six files and used in exactly one: `research.py:11` (used at `:86`). The
  other five imports are dead and belong to `DAB-194`. `jinja2` itself stays in `requirements.in`.
