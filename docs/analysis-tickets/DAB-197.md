## Context

`_convert_pdf_to_images_sync` renders each page to a MuPDF pixmap, **encodes it to PNG**, and then
**decodes that PNG back** into a PIL image. `pix.samples` is already an RGB buffer. The round trip
is pure waste.

Two reports disagreed about this code. One said the bottleneck is the single-worker executor and
proposed widening it. The other measured both and found the executor width buys **1.21x** while
deleting the round trip buys **11.7x-16.5x**. The reconciliation adjudicated in favour of the
second and **retracted the "expected 4x" from widening the pool**.

BEFORE, `src/bot/discord_bot.py:1178-1184`:

```python
                        # Render page to pixmap (image) at configured resolution
                        mat = fitz.Matrix(self.config.pdf_render_scale, self.config.pdf_render_scale)
                        pix = page.get_pixmap(matrix=mat)

                        # Convert pixmap to PIL Image and ensure RGB mode
                        img_data = pix.tobytes("png")        # PNG ENCODE
                        image = Image.open(io.BytesIO(img_data))   # PNG DECODE of what we just encoded
                        image = self._convert_image_to_rgb(image)
```

AFTER: `Image.frombytes("RGB", (pix.width, pix.height), pix.samples)`.

Measured (`/tmp/i3-perf/bench_pdf2.py`):

| render | 20 pages @scale 2.0 | per page | 20 pages @1.5 | @1.0 |
|---|---|---|---|---|
| shipped (`tobytes("png")` -> `Image.open`) | **1.634 s** | 81.7 ms | 0.949 s | 0.285 s |
| direct (`Image.frombytes("RGB", ..., pix.samples)`) | **0.140 s** | **7.0 ms** | 0.069 s | 0.041 s |
| speedup | **11.67x** | | 13.80x | 6.98x |

Pixel identity, verified by comparing `img.tobytes()`:
`pixel-identical to the shipped path: True (1190x1684 both)`.

Independent reproduction on a 3-page fixture at scale 2.0:

```
  shipped round-trip                                     210.9 ms
  direct Image.frombytes("RGB", (w,h), pix.samples)       12.7 ms      -> 16.55x
```

The executor-width measurement that must **not** be acted on:

| | w=1 | w=4 | w=8 |
|---|---|---|---|
| shipped, 8 concurrent jobs | 13.59 s | 11.50 s | 11.23 s |
| **direct**, 8 concurrent jobs | **1.42 s** | **0.84 s** | 0.89 s |
| direct, `ProcessPoolExecutor` | — | 0.46 s | **0.27 s** |

Widening `max_workers` alone is **1.21x**. The work is GIL-bound in the PNG round trip.

A thread-safety probe (8 threads x 3 concurrent conversions of independent documents, PyMuPDF
1.28.0 / MuPDF 1.29.0) found 0 errors, so the `max_workers=1` comment at `discord_bot.py:316-317`
("concurrent conversions are not safe within this process") does not reproduce on this version for
independent `fitz.open(stream=...)` documents. **One negative probe is not a safety proof.**

The original observation that motivated the wrong fix is still worth recording: at
`max_pdf_pages: 20` and `pdf_render_scale: 2.0` the shipped path costs ~1.12 s per attachment,
executed one at a time process-wide, so 10 concurrent PDF uploads means the last user waits ~11.2 s
of pure queueing.

## Acceptance criteria

- [ ] `_convert_pdf_to_images_sync` constructs the PIL image directly from `pix.samples`; no PNG
      encode and no `Image.open` on the hot path.
- [ ] Output is **pixel-identical** to the previous path: `img.tobytes()` matches, and
      `image.mode == "RGB"`.
- [ ] A 20-page render at scale 2.0 completes in roughly 0.14 s rather than 1.6 s.
- [ ] `max_workers` stays at **1**. Do not widen it in this ticket.
- [ ] Non-RGB pixmaps (CMYK, alpha) are still handled correctly.

## Files to touch

- `src/bot/discord_bot.py:1178-1184` only. Nothing else.

The three-line swap:

- delete `img_data = pix.tobytes("png")` (`:1182`);
- delete `image = Image.open(io.BytesIO(img_data))` (`:1183`);
- construct directly: `Image.frombytes("RGB", (pix.width, pix.height), pix.samples)`.

**Keep** `self._convert_image_to_rgb(image)` at `:1184`. It becomes a near no-op for RGB pixmaps but
keeps the CMYK/alpha path honest — and an existing test patches it (see Risks). Check `pix.n` /
`pix.alpha` before hard-coding `"RGB"`: a pixmap with an alpha channel has 4 samples per pixel and
`Image.frombytes("RGB", ...)` would misinterpret the buffer.

## Risks and notes

- **Two existing tests are load-bearing here:**
  - `tests/test_pdf_processing.py:55`
    `test_rasterization_and_pillow_conversion_run_in_worker_thread` patches
    `bot._convert_image_to_rgb` (`original_convert = bot._convert_image_to_rgb` at `:59`) to record
    thread ids. Keeping the `_convert_image_to_rgb` call at `:1184` keeps this test valid.
  - `tests/test_pdf_processing.py:105` `test_concurrent_conversions_never_overlap` pins
    single-worker serialisation. It is the test that would have to change if anyone widened the
    pool — which is the reason not to.
- The other four tests in that file (`:77`, `:91`, `:155`, `:204`) exercise the page limit, invalid
  PDFs, cancellation and executor drain; none should be affected.
- **Do not widen `max_workers` as part of this ticket.** If widening is ever revisited it needs a
  real stress test, and the comment at `discord_bot.py:316-317` must be updated or refuted first.
- This sits on the **same** single worker thread that `DAB-198`'s 107-second resource bomb occupies.
