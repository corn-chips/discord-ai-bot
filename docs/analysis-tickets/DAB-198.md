# DAB-198: PDF resource bomb — a 3,630-byte upload costs 107 s CPU and 1.63 GB RSS and returns nothing

**Status: PARTIAL** — the per-page pixel clamp landed in `4fb091c` and closes the S1 as filed; **seven of the eight acceptance criteria below are untaken.** This ticket still lands **first**, and DAB-197's PNG round-trip deletion follows it inside the same commit: until the clamp exists, the `Image.open` DAB-197 removes is the only thing stopping a 256 MP allocation (`ANALYSIS_CORRECTIONS.md` item 6). Re-measured at `083ebea` on this ticket's own 3,630-byte fixture: **20 pages in 5.8 s at 3.3 GB peak**, against **40.0 s and 20.7 GB** with the clamp defeated on the same box. Do not compare either against the "107 s, 1.63 GB, returns nothing" figure in the title — that was measured on a host where MuPDF's allocation was *refused*, and comparing a refused render against one that succeeds is not a comparison. **The live residual is spend, not memory**: the clamp is per-page, so the fixture still rasterises to **792 MP** with no total-megapixel budget, no wall-clock timeout, no `attachment.size` gate, and nothing between the renderer and the paid Gemini request that bounds what is sent (merged ID `C4-15`). The page loop still `continue`s rather than breaking, and a zero-page PDF still returns silence.

## Context

The page-*count* guard works: `max_pdf_pages` (default 20) clamps before rendering, so a
20,000-page PDF costs 0.07 s. Keep it.

There is no page-*area* guard, no total-megapixel budget, no attachment size gate on the PDF branch,
and **no wall-clock timeout anywhere on the PDF path**. An 8000x8000 pt MediaBox is legal PDF (spec
limit 14400) and at `pdf_render_scale: 2.0` yields a 16000x16000 px = 256 MP pixmap. MuPDF allocates,
then aborts with `code=5: Overly large image`. The per-page `except Exception: continue` swallows it
and moves to the next page — so the cost is paid **20 times** and nothing is produced.

## Reproduction

Build the fixture above, then call `_convert_pdf_to_images_sync(pdf_bytes, "poison.pdf")` on a
`DiscordBot` built with `object.__new__` and a `SimpleNamespace` config
(`max_pdf_pages=20, pdf_render_scale=2.0`). Guard the host with
`resource.setrlimit(resource.RLIMIT_AS, 6 * 1024**3)` first.

## Acceptance criteria

- [ ] Before `get_pixmap`, total rendered pixels are capped:
      `w, h = page.rect.width * scale, page.rect.height * scale`; if `w * h > MAX_RENDER_PIXELS`,
      reduce `scale` to `sqrt(MAX_RENDER_PIXELS / (page.rect.width * page.rect.height))`. A 40 MP
      cap keeps every legitimate document.
- [ ] A total-megapixel budget applies across all pages of one attachment, not just per page.
- [ ] The executor call is wrapped in `asyncio.wait_for(..., timeout=config.pdf_conversion_timeout)`.
- [ ] The page loop **breaks** after N consecutive failures instead of `continue`, so a poison
      document costs one page, not twenty.
- [ ] The 3,630-byte 20-page fixture returns in under a second, not 107 s.
- [ ] Peak RSS for that fixture stays bounded (no 1.6 GB spike).
- [ ] An `attachment.size` gate is applied to the PDF and image branches **before**
      `await attachment.read()`.
- [ ] The user is told when a PDF produced zero pages, instead of receiving silence.

## Risks and notes

- **Severity is contested and the disagreement is informative.** An independent verification pass
  reproduced every number and then rated it **S2**, not S1, because the work is offloaded to
  `self._pdf_executor` (`discord_bot.py:318`, `:1145`) so the gateway heartbeat is **not** blocked,
  the process survives, and nothing is corrupted. It also added an aggravating factor the original
  finding omits: because it is a *single*-worker executor, one attacker serialises PDF conversion
  for the whole bot, and nothing bounds the queue. Its verdict: "**It becomes S1 on any host with
  < 2 GB of memory**, where the 1.63 GB spike is an OOM kill." The target deployment is a hobbyist's
  home box.
- Where the failure actually surfaces: PIL's decompression-bomb guard fires
  (`Image.open` -> `DecompressionBombError`) *after* MuPDF has already spent the CPU and made the
  768 MB pixmap allocation. **The guard prevents decoding, not the resource burn.** Do not rely on
  it.
- Existing tests on this path (6, class `PdfProcessingTest` at `:13`): `:55`, `:77`, `:91`, `:105`,
  `:155`, `:204`. `:77 test_page_limit_and_images_remain_usable_after_worker_cleanup` covers the
  page-count guard and must stay green. `:105 test_concurrent_conversions_never_overlap` pins
  single-worker serialisation — relevant if anyone tries to widen `max_workers`; do not.
- ~~Land `DAB-197` first.~~ **CORRECTED 2026-07-31 — land this clamp first; see line 13.** The
  observation behind the original wording still holds and is worth keeping: with the 11.7x round
  trip removed, a 20-page legitimate render costs 0.14 s, so a timeout of a few seconds is generous
  rather than arbitrary. Size the budget *after* both changes are in, not by reordering them.
- Two cheap adjacent fixes worth folding in: `C4-17` (`DAB-200`) — verify `pdf_bytes[:5] == b"%PDF-"`
  at `discord_bot.py:1161`, since `filetype="pdf"` is not enforced and any MuPDF-supported format is
  reachable from a `.pdf` filename; and `C4-18` (part of `DAB-006`) — tell the user when a PDF
  yields zero pages.
