# DAB-204: `test_main_response_path_does_not_wrap_client_retry_timeout` actively blocks the whole-sequence-deadline fix

- Type: BUG
- Severity / Payoff: S2 — "a regression test that *blocks the correct fix* for a real defect is
  worse than a missing test"
- Effort: S — one test rewrite
- Priority score: 3.0 — impact High (3) x frequency Rare (1) / effort S (1)
- Confidence: **VERIFIED** — mutation-tested three ways against a `/tmp` copy
- Merged IDs: `C7-F1`
- Blocks / Blocked by: **blocks `DAB-042`.** Do this first, or a correct implementation of the
  whole-sequence deadline fails the suite and the failure message lies about why.

## Context

BUG-0001 ("Main response timeout cancels configured Gemini retries") was fixed in `88e330b` by
**deleting** the outer `asyncio.wait_for` around `generate_response` rather than by widening it. The
regression test written in that same commit asserts the *absence of a call name*, not a behaviour.

`DAB-042` now needs the opposite thing — a whole-sequence deadline — and the existing test fails a
correct implementation of it. Worse, the failure surfaces as a misleading `TypeError` because the
coordinator's blanket `except Exception` swallows the `AssertionError`. A maintainer hitting it will
read the test's name and conclude their fix is wrong.

## Evidence

The test: `tests/test_bug_regressions.py:110`.

```python
    async def test_main_response_path_does_not_wrap_client_retry_timeout(self):
```

What it asserts, `tests/test_bug_regressions.py:150-163`:

```python
        with patch(
            "src.bot.discord_bot.asyncio.wait_for",
            side_effect=AssertionError("outer wait_for must not own Gemini retries"),
        ):
            await DiscordBot._generate_and_send_response(
                bot,
                message,
                "prompt",
                [],
                show_status_message=False,
            )

        gemini_client.generate_response.assert_awaited_once()
        bot._send_response_safely.assert_awaited_once()
```

Because `src.bot.discord_bot.asyncio` *is* the singleton `asyncio` module, that patch is effectively
**global** and does reach `response_generation.py`.

The unwrapped call today, `src/bot/response_generation.py:405-418`:

```python
                    api_response = await self.gemini_client.generate_response(
                        enhanced_prompt,
                        context,
                        ...
                    )                                     # no wrapper, no outer budget
```

**Three mutations were run against a `/tmp/c7probe` copy:**

*Mutation 1 — reintroduce the exact bug* (`wait_for(generate_response(...), timeout=t+10)`):

```
AssertionError: outer wait_for must not own Gemini retries        <- raised
FAILED (errors=1)
```

**Catches it.** But the coordinator's blanket `except Exception` swallows the `AssertionError` and
the surfaced failure is `TypeError: object Mock can't be used in 'await' expression`. A maintainer
would not learn *why* from the failure message.

*Mutation 2 — the same bug via the modern idiom* (`async with asyncio.timeout(api_timeout):`):

```
Ran 1 test in 0.005s
OK                                                                 <- BLIND
```

**Does not catch it.** The test guards a *call name*, not the behaviour.

*Mutation 3 — the fix `DAB-042` would recommend* (a **correct** whole-sequence deadline:
`wait_for(..., timeout = per_attempt x (max_retries+1) + 30)`):

```
FAILED (errors=1)
```

**The regression test actively fails a correct implementation.**

The swallowing handler, `src/bot/response_generation.py:488-492`:

```python
                except Exception as exc:
                    error_context = self.error_manager.create_error_context(exc)
                    self.error_manager.log_error(
                        error_context,
                        "Unexpected error during response generation for message "
                        f"{message.id}",
                    )
```

Why a whole-sequence deadline is needed at all (the thing this test is standing in front of):
`max_retries: 3`, `timeout: 30`, `extended_timeout: 120`, and `get_timeout_for_model`
(`gemini_client.py:299-317`) returns `extended_timeout` for any thinking level in
`{low, medium, high}`. A virtual-clock probe of `_run_response_attempts` with every attempt timing
out gives `480.0 s`; the analytic upper bound including backoff is `488.5 s`. Timeout ownership today
is solely in `GeminiClient._execute_response_attempt` (`gemini_client.py:1199`).

Dead residue the same fix left behind: `response.api_timeout_buffer: 10` was parsed into
`BotConfig.api_timeout_buffer` and read by nothing — it was the `+ 10` the fix deleted. **It no
longer exists.** `9894bcc` deleted all three sites (the `config.yaml` key, the `BotConfig` field
and the `config_helpers.py` parser), so a whole-sequence budget cannot reuse it and must add a
**new** key through all four places. The lines this ticket originally cited now hold other
settings: `config.yaml:61`, `src/config.py:78` and `src/config_helpers.py:244` are all
`response.max_retries` today.

## Reproduction

Copy the repo to `/tmp`, apply this mutation to `src/bot/response_generation.py:405`, and run
`python -m unittest tests.test_bug_regressions` **in the copy**:

```python
api_response = await asyncio.wait_for(
    self.gemini_client.generate_response(...),
    timeout=per_attempt * (self.config.max_retries + 1) + 30,   # a CORRECT deadline
)
```

The suite fails. **Do not apply this to the working tree.**

## Acceptance criteria

- [ ] The `patch("src.bot.discord_bot.asyncio.wait_for", side_effect=AssertionError(...))` is gone.
- [ ] The test asserts the **budget** instead: any deadline observed is
      `>= per_attempt x (max_retries + 1)`. This is idiom-independent and passes under both
      `asyncio.wait_for` and `async with asyncio.timeout(...)`.
- [ ] It optionally also asserts **retry-count survival** directly: under an all-timeout stub, count
      `generate_response` / `_execute_response_attempt` invocations and assert all
      `max_retries + 1` ran.
- [ ] Mutation 1 (a too-tight outer wrapper) still **fails** the rewritten test.
- [ ] Mutation 2 (the `asyncio.timeout()` idiom with a too-tight budget) now **also fails** — it
      currently passes silently.
- [ ] Mutation 3 (a correct whole-sequence deadline) **passes**.
- [ ] The failure message is legible: an assertion failure no longer masquerades as a `TypeError`.

## Risks and notes

- **The incumbent's name is part of the trap.** Anyone fixing `DAB-042` will hit this failure, read
  "must not wrap client retry timeout", and conclude their fix is wrong. Say so in the commit
  message and in the new test's docstring.
- The `except Exception` change at `response_generation.py:488` has wider blast radius than the test
  rewrite — it changes which exceptions reach the user-visible error path. Land it as a separate
  commit so it can be reverted independently. If you skip it, the rewritten test should assert
  **outside** the coordinator so its failures are legible.
- This is one of two live test obstructions in the codebase; the other is `DAB-203`. Both are
  Sprint-2 unblockers and neither touches production behaviour.
- The reconciliation's verdict on the incumbent: "**VALID but over-specified + idiom-blind.** Catches
  the literal bug; **blind** to `asyncio.timeout()`; **fails a correct whole-sequence deadline**.
  Failure surfaces as a misleading `TypeError` because `except Exception` swallows the assertion."
