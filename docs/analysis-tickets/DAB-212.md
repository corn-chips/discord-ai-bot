# DAB-212: `get_pending_embeddings` sorts on the joined table, forcing a temp B-tree on every poll

- Type: IMPROVEMENT
- Severity / Payoff: **1844x** measured (127.666 ms -> 0.069 ms). No index, no migration, two lines.
- Effort: XS
- Priority score: 16.0 — impact Medium (2) x frequency Continuous (4) / effort XS (0.5)
- Confidence: **VERIFIED** — `EXPLAIN QUERY PLAN` before and after, timed
- Merged IDs: `I2-09`. New canonical ID — this proposal has no bug-register counterpart, so it is
  allocated from the range above `DAB-211`.
- Blocks / Blocked by: **none.** "This can ship today, ahead of everything else."

## Context

`get_pending_embeddings` does `ORDER BY m.created_at DESC LIMIT 16`. `created_at` lives on the
*joined* table, so SQLite drives from `idx_message_embeddings_status`, joins every pending row to
`message_index`, materialises the lot, sorts it, and throws away all but 16.

The embedding worker calls this in a loop.

A Discord snowflake is monotonic in creation time, and `message_id` is the primary key of both
tables. Ordering by `e.message_id DESC` is *semantically identical* and lets the existing index
supply the order.

Measured (`/tmp/i2lab/eqp2_output.txt`):

```

    SEARCH e USING INDEX idx_message_embeddings_status (embedding_model=? AND embedding_status=?)

    >>> best 127.666 ms | median 132.027 ms

Q4b rewrite  ORDER BY e.message_id DESC
    SEARCH e USING INDEX idx_message_embeddings_status (embedding_model=? AND embedding_status=?)
    SEARCH m USING INTEGER PRIMARY KEY (rowid=?)
    >>> best 0.069 ms | median 0.073 ms

Q4 speedup: 127.666 -> 0.069 ms = 1844x ; +COALESCE 0.070 = 1821x
```

**1844x from deleting one temp B-tree.**

## Files to touch

- `src/services/message_index_service.py` — exactly the `ORDER BY` at `:1199`, plus a comment.
  Optionally the `next_retry_at` predicate at `:1195`. Nothing else.

```diff
-                      ORDER BY m.created_at DESC
+                      -- Snowflake IDs are chronological, and message_id is the PK of both
+                      -- tables, so this is the same order the index already provides.
+                      ORDER BY e.message_id DESC
                       LIMIT ?
```

Optional second rewrite, equivalent in cost — take it for readability, not speed:

```diff
-                     AND (e.next_retry_at IS NULL OR e.next_retry_at <= ?)
+                     AND COALESCE(e.next_retry_at, '') <= ?
```

An optional companion index, **not required** for the 1844x:

```sql
CREATE INDEX IF NOT EXISTS idx_message_embeddings_pending
    ON message_embeddings (embedding_model, message_id DESC)
    WHERE embedding_status = 'pending';
```

## Risks and notes

- **All nine existing call sites were checked; none asserts ordering, so the rewrite is
  test-safe.** Verify this in review:
  - `tests/test_message_rag_services.py:60` — result collected into a **dict** comprehension.
  - `:128` — collected into a **set**, asserted with `assertIn(304, pending_ids)`.
  - `:202`, `:219`, `:250` — dict / membership assertions.
  - `:271` `test_pending_embedding_batches_can_be_scoped_to_one_channel` — call at `:285`, assertion
    is `assertEqual([message_id for message_id, _text, _hash in pending], [384])`, a
    **single-element** list, so order-insensitive in practice.
  - `:520`, `:566`, `:587` — `get_pending_embeddings_async` is an `AsyncMock` in
    `RagPregenerationTest`; the SQL is not exercised.
- **The behavioural caveat that must go in the code as a comment:** bot responses are indexed with
  `created_at=datetime.now()` (`index_bot_response`, `:390`) while their `message_id` is Discord's.
  These stay consistent because Discord assigns the ID at send time, but a caller passing an
  explicit back-dated `created_at` would order differently. The embedding queue does not care about
  exact order, only about draining, so this is safe — but say so where the next reader will look.
- Rollback is reverting two lines.
- This is the single cheapest measured win in the corpus. There is no reason for it to wait behind
  anything.
