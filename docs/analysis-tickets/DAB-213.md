# DAB-213: No cooldown on any slash command; one scripted user can burn four figures an hour

**Status: LANDED** in `b9a4514` — `/deepresearch` and `/summarize` are capped at 1/min and 4/h per user, measured 5.13e9 -> 2.42e7 tokens/h worst case. **The premise is wrong in the commit message and in this ticket:** those commands were governed by *no* rate limiter, not by the 60/h text limit, which is charged only from `on_message`. See `ANALYSIS_CORRECTIONS.md` item 17. The cap is `expensive_command_limiter`, a second `RateLimiter` instance, not the `app_commands.checks.cooldown` decorator this ticket prescribes — which is why `DAB-032`'s O(n) rebuild now has two call sites rather than one.

- Type: IMPROVEMENT
- Severity / Payoff: worst-case single-user hourly exposure **~$3,247/h -> ~$0.90/h** for the
  dominant vector (~3,600x). Token counts are assumption-free; dollar figures are not (see Risks).
- Effort: S — decorators plus one error handler, no schema, no migration
- Priority score: 8.0 — impact Critical (4) x frequency Occasional (2) / effort S (1)
- Confidence: **VERIFIED** for the absence of any cooldown; **modelled** for the cost
- Merged IDs: `B7-20` (`DAB-158`); the design and the numbers are `I4-07` layer 1. New canonical ID —
  allocated from the range above `DAB-211` because this is a proposal with no bug-register
  counterpart at this scope.
- Blocks / Blocked by: blocked by `DAB-203` only to the extent that you want a de-brittled tree test
  to prove the decorators did not change the command surface. It should not.

## Context

Only *text* messages are rate-limited (`text_rate_limit_per_minute: 10`,
`text_rate_limit_per_hour: 60`, enforced at `discord_bot.py:799` and
`live_message_coordinator.py:229`).

`/deepresearch`, `/summarize` and `/rag backfill` pass through **no limiter of any kind**, and none
of them checks any permission. There is no `@app_commands.checks.cooldown` anywhere in
`src/bot/command_modules/`.

discord.py ships this. The bot simply never used it.

## Evidence

All three commands live in `src/bot/command_modules/research.py`:

| command | decorator | callback | registrar | body span |
|---|---|---|---|---|
| `/deepresearch` | `:38` | `:40` `async def deepresearch(interaction, topic: str)` | `:31` `def register_deepresearch_command` | `:38-129` |
| `/rag backfill` | `:200` | `:202` `async def rag_backfill(interaction, limit=None)` | inside the `rag_group` registrar | `:200-240` |
| `/summarize` | `:302` | `:303` `async def summarize(interaction)` | `:295` `def register_summarize_command` | `:302-392` |

Supporting call sites: `/deepresearch`'s two Gemini calls at `research.py:59-65` (gather, with
`search_override=True` at `:64`) and `:104-110` (synthesis); `/summarize`'s history read at `:313`
and generation at `:359`; `/rag backfill` -> `start_channel_pregeneration` at `:219`, with guards at
`:203`, `:207`, `:211` and `rag.backfill_limit` read at `:217`.

**Modelled worst-case exposure, one user, one hour** (from `/tmp/i4/cost_model.py`):

*Vector A — text messages (rate-limited to 60/h).* Worst case is a channel carrying a 100 KB pin
(`DAB-073`): 26,869 input tokens, `max_output_tokens_high` = 65,536, `max_retries: 3` -> 4 attempts.

```
ceiling   60 x 4 x (26,869 + 65,536) = 22,177,200 tok   ~ $41.26/h
plausible (full out on the final attempt only)          ~ $15.45/h
```

*Vector B — `/deepresearch`, no cooldown.* Per invocation: gather at
`max_output_tokens_medium` = 16,384 with Google Search, then synthesis at
`max_output_tokens_high` = 65,536 over the gathered text. **100,904 tokens = $0.2255** (x4 with
retries = $0.9020).

| rate | plausibility | tokens/h | $/h | with retries |
|---|---|---|---|---|
| 60/h | a human clicking once a minute | 6,054,240 | **$13.53** | $54.12 |
| 600/h | a keyboard macro | 60,542,400 | **$135.30** | $541.19 |
| 3,600/h | a script | 363,254,400 | **$811.78** | **$3,247.13** |

*Vector C — `/summarize`, no cooldown*, up to `channel_history_limit: 500` messages in one prompt:
30,346 tok = $0.0189/call -> $67.91/h at 1/s.

*Vector D — `/rag backfill`, no cooldown, no permission check*, `rag.backfill_limit: 0` meaning *the
entire accessible history*: a 50k-message channel is 2.5M embedding tokens = $0.38; across 20
channels, $7.50 per sweep. There *is* a per-channel "already running" guard — the only spend control
that exists in the whole bot.

Headline: **a single user with a script can burn ~363 million tokens in one hour through
`/deepresearch` alone.** A *human* doing it by hand at 10/minute reaches ~$135/h. An **unlucky,
non-malicious** user in a channel with a large pin reaches ~$15/h. And **none of it appears in
`token_usage`**: only successful main-model calls are recorded, i.e. ~25% of a high-tier turn's
tokens, and 0% of retries.

## Risks and notes

- **Every dollar figure is assumption-dependent. The token counts are not.** There is no price data
  in this repo, and the configured model ids are preview ids whose list price cannot be sourced from
  the repo. The model used:

  | model | in | out | thinking (billed as out) | cached in |
  |---|---|---|---|---|
  | `gemini-3-flash-preview` | 0.30 | 2.50 | 2.50 | 0.075 |
  | `gemini-3.1-pro-preview` | 1.25 | 10.00 | 10.00 | 0.31 |
  | `gemini-2.5-flash-lite` | 0.10 | 0.40 | 0.40 | 0.025 |
  | `gemini-embedding-2` | 0.15 | — | — | — |
  | `gemini-2.5-flash-image` | 0.30 | 30.00 | — | 0.075 |

  USD per 1M tokens, **operator-supplied, not vendor-verified**. Substitute real prices into
  `/tmp/i4/cost_model.py:USD_PER_MTOK` and re-run for real numbers. Also note prompt tokens are
  estimated as chars / 4.0 because `sentencepiece` is not installed; the constant is applied
  identically to "today" and "proposed", so the *ratios* are robust.
- **New user-visible failure mode.** `CommandOnCooldown` must be rendered. The
  `on_app_command_error` handler is not optional.
- **`/rag backfill` gaining `manage_guild` is a behaviour change** for non-admin users who use it
  today. Under the hobbyist threat model that is proportionate — it is the single most expensive
  operation in the bot — but say so in the release notes.
- **Cooldowns cap *frequency*; budgets cap *magnitude*.** Layer 1 does **not** cover Vector A (60
  legal messages each costing 20x normal). That needs a token budget
  (`user_tokens_per_hour: 150000`, a `spend_window` table, `on_exceed: "degrade"`), which is a
  larger M-effort change depending on a usage fact table. Combined, layers 1 and 2 take worst-case
  single-user hourly exposure from ~$3,247 to roughly $2 — about 1,600x.
- **Adding decorators must not alter the command tree.** The three pinned counts in
  `tests/test_command_registration.py` (`== 22` at `:147`, `== 35` at `:148`, the `[5:10]` slice at
  `:239`) are the guard. They should hold; re-run them.
- The cheapest complementary pair, per the cost lane's own "suggested first PR": this ticket plus
  `DAB-150` (bound pins at ingest) plus capping `max_output_tokens_high` from 65,536 to 16,384.
  Together those cut worst-case single-user hourly exposure to well under $10 without touching the
  database, the command tree, or any migration.
