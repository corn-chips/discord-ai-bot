1) System Overview

Ingress

Discord Gateway

Events enter through on_ready, on_message, and slash command handlers on the bot command tree.

Core Runtime

DiscordBot

Coordinates context collection, multimodal extraction, model routing, Gemini calls, rendering, and send/retry behavior.

LLM Layer

GeminiClient

Formats prompt envelopes, toggles search, applies safety configs, streams or non-streams responses, and normalizes finish reasons.

Image Layer

ImageProcessingService

Queue + worker model for image edit/generate jobs backed by NanoBananaClient and user/global rate controls.

Post Processing

Render + Split

LaTeX/table rendering with attachment generation, plus intelligent splitting and embed paginator for long outputs.

State

SQLite Services

Token usage, channel personality, user preferences, pins, and hidden-message restoration all share one DB file path.

2) Startup Pipeline

main.py
  -> load .env
  -> load_and_validate_config() + setup_logging()
  -> validate_startup_connectivity()
  -> DiscordBot(config)
       -> ContextCollector
       -> GeminiClient
       -> MessageSplitter
       -> ContentRenderer
       -> UserExperienceService
       -> TokenTracker (optional)
       -> ImageProcessingService (optional, if API key)
       -> EnhancedCommandHandler (optional, requires image service)
  -> bot.start(discord_token)

on_ready()
  -> start image workers (if enabled)
  -> setup slash commands
  -> tree.sync() global commands
  -> set bot presence

Configuration Load Order

.env supplies secrets; config.yaml supplies operational settings. Validation exits hard on missing critical keys.

Conditional Services

Image services and enhanced command router are only initialized when image config is available and starts cleanly.

3) Mention Message Flow (Primary Runtime Path)

Discord message create
  -> ignore if author.bot
  -> pass if is_bot_mentioned(message) OR DM channel
  -> per-user text rate limiter (minute/hour)
  -> EnhancedCommandHandler.handle_message() [if enabled]
       -> handled? yes: stop
       -> handled? no: set model by router complexity
  -> extract user prompt (remove bot mention, @everyone, @here)
  -> if empty prompt: reply "no message found" and stop
  -> collect context (reply-aware)
  -> generate_and_send_response()
       -> ingest images/pdf/audio/files
       -> build enhanced prompt
       -> personality + user preferences
       -> GeminiClient.generate_response()
       -> render/split/send response
       -> send grounding sources (if present)
       -> persist token usage
Stage What It Does Important Branches
Ingress Gate Accepts DM messages automatically; in guild channels requires mention, reply-to-bot, or mentioned role on bot member. Explicitly ignores @everyone/@here as trigger sources.
Text Rate Limit Per-user limiter tracks rolling 1-minute and 1-hour windows. Returns user-facing retry messages with computed wait time.
Router Pass Classifies intent + complexity when enhanced handler is active. If intent handled (image edit/generate), text pipeline exits early.
Context Build Uses complexity tier to choose context window and merges reply-context + channel-context with dedup. For image generation intent fallback, context is forced minimal.
Generation Phase Collects multimodal payloads, builds prompt envelope, and calls Gemini with timeout wrapper. Unsupported files are reported to channel as informational note.
Delivery Phase Post-processes content, splits if needed, replies to original message, and appends sources when grounded. Long responses become paginated embeds with sender-priority navigation.

4) Enhanced Intent Router (When Image Service Is Enabled)

Router Model

gemini-2.5-flash-lite classifies each mentioned message into:

image_generate, image_edit, or text plus complexity low|medium|high.

Decision cache key is normalized message text + has_images, with LRU size and TTL from config.

image_editRequires image attachment; otherwise sends upload guidance embed.

5) Multimodal Ingestion Pipeline

Images + PDFs

Image sources are gathered from:

1) current message attachments, 2) replied message attachments, 3) recent context messages (bounded).

PDF attachments are rendered page-by-page to images (PyMuPDF), capped by max_pdf_pages.

Every image receives metadata linking image order to source message id/time/attachment index.

Audio + Text Files

Audio is extracted from current/replied attachments using content-type, voice-message flags, and extension fallback mapping.

Text files are loaded from current/replied attachments if extension/type is supported and size is below max_text_file_size_bytes.

Decode attempts: utf-8, latin-1, cp1252, ascii.

Input ClassAcceptedRejected / Routed Elsewhere
Image AttachmentLoaded as PIL image and converted to RGB-
PDF AttachmentConverted to image pagesNot treated as text-file content
Audio AttachmentBytes + MIME packed for modelNon-audio attachments skipped
Text AttachmentDecoded and injected into prompt blockOversize/unsupported/encoding-failed files listed to user

6) Prompt Assembly and Context Envelope

Final prompt assembly order (GeminiClient.format_prompt):
  1) System instruction (low/medium/high + optional thinking addon)
  2) [TONE INSTRUCTION] from channel personality (if set)
  3) [LANGUAGE INSTRUCTION] from user preference (if not auto)
  4) Chronological context block with stable labels: CTX_MSG_###
  5) Image context mapping block: IMG_# -> source message mapping
  6) Current user message
  7) "Grok:" response cue

File Prompt Augmentation

If text files were uploaded, file contents are prepended in a structured section with filename, size, and fenced content.

If no user text exists and files are present, an auto-generated analysis prompt is used.

Audio and Image Defaults

Audio-only payloads get a verbatim-transcription default prompt. Image-only default prompt exists in generation stage.

Note: early empty-prompt guard in on_message can stop some no-text mention paths before this stage.

7) Gemini Execution Engine

Request Build

Search usage is decided by explicit override or heuristic scan (URLs, search terms, and live-data terms).

When search is enabled and content is multimodal, implementation currently falls back to text-only content for compatibility.

Safety settings, temperature/top-p/top-k, and max output tokens are loaded from config by complexity tier.

Retry + Finish Logic

Each call supports retry loop with timeout handling and exponential backoff (plus retry-after hints from error manager).

Finish reason normalization drives response branching: STOP, MAX_TOKENS, SAFETY, RECITATION, other.

Successful responses add model header; search-enabled calls also add grounding marker and source extraction.

Gemini call state machine 
for attempt in [0..max_retries]
  call _generate_response_async() within timeout
    if stream callback configured -> accumulate chunks
  if response missing -> empty_response
  if finish_reason == STOP -> success
  if finish_reason == MAX_TOKENS + text -> success + truncated note
  if finish_reason == SAFETY -> safety_filter error
  if finish_reason == RECITATION -> recitation error
  else -> unknown_finish_reason error

on timeout:
  retry until attempts exhausted, then timeout error
on exception:
  ErrorManager classifies + may retry (with retry_after/backoff)
User model preference can override router-selected model before the final Gemini call.

8) Response Rendering and Delivery

Post-processing

ContentRenderer.process_response() runs before sending:

- wraps raw LaTeX patterns, renders complex equations into one PNG attachment,

- converts markdown tables into fixed-width code blocks for Discord readability.

Delivery Strategy

If output length <= 2000 chars: direct reply.

If > 2000 chars: intelligent split + paginated embed view with left/right buttons and sender-priority window.

Grounding links (up to 10) are sent as a follow-up reply message to the bot response.

_send_response_safely()
  -> validate non-empty content
  -> render LaTeX/tables (may produce image attachments)
  -> split or direct reply
  -> optional sources reply
  -> map Discord exceptions to user-friendly fallback messages

9) Image Job Queue Pipeline

Entry Points

1) Mention router path (EnhancedCommandHandler) for natural-language edit/generate.

2) Slash command path (/edit-image) for explicit attachment + instruction.

Queue Core

ImageProcessingService validates request, enforces per-user hourly limits, enqueues jobs, and processes via worker tasks under a semaphore.

submit image edit
  -> validate image + instruction
  -> user rate-limit check (per hour)
  -> create ProcessingJob + enqueue
  -> worker picks job (bounded concurrency)
       -> validate image bytes
       -> NanoBananaClient.edit_image(...)
       -> update status/progress/result
       -> signal completion_event
  -> caller waits (mention path) or polls (slash path)
  -> send edited/generated image or error message
ControlWhereBehavior
Global image request pacingNanoBananaClientTracks request timestamps per minute and delays when at cap.
User image rate limitImageProcessingServiceRejects after configured requests/hour with reset guidance.
Job cleanupImageProcessingServicePeriodic cleanup task prunes old completed jobs.

12) Edge Cases and Current Gotchas

Behavior Note

Pinned-memory service has a prompt formatter (get_pins_for_prompt) but mention pipeline does not currently inject it into Gemini prompts.

Behavior Note

When online search is active with multimodal input, request payload is reduced to text-only in Gemini async call path.

Behavior Note

Empty user prompt is rejected early in on_message, which can prevent no-text mention scenarios from reaching default image/audio prompt logic.

Behavior Note

Router complexity selection can be overridden later by user preferred model, changing final model from initial complexity decision.
